## Project Overview

Royal Conceito — an e-commerce backend for a clothing store, built with Django 6 + Django REST Framework. Brazilian Portuguese is used for model/field names and UI. The frontend (React/Vite) is under active development (Phase 4) in `frontend/`.

## Common Commands

All commands run from `backend/`:

```bash
# Activate virtualenv
source .venv/bin/activate

# Run dev server
python manage.py runserver

# Database migrations
python manage.py makemigrations
python manage.py migrate

# Run tests
python manage.py test
python manage.py test produtos    # single app

# Create admin user
python manage.py createsuperuser

# Install dependencies
pip install -r requirements.txt
```

## Architecture

**Monolithic Django project** with three apps under `backend/`:

- **core/** — Project settings, root URL config, JWT token endpoints
- **produtos/** — Product catalog (Categoria, Marca, Produto, Variacao)
- **pedidos/** — Order processing (Pedido, ItemPedido, Endereco) + business logic signals
- **usuarios/** — User registration (uses Django's built-in User model)

### Data Flow

```
HTTP Request → DRF Router → ViewSet → Serializer → Model/ORM → Signal → SQLite
```

All API endpoints use DRF's `DefaultRouter` with `ModelViewSet`. Each app registers its own router in its `urls.py`, and `core/urls.py` includes them all under `/api/`.

### Key Model Relationships

- **Produto** → has many **Variacao** (size variants with stock tracking, CASCADE)
- **Produto** → belongs to **Marca** and **Categoria** (both SET_NULL)

`produtos/management/commands/importar_produtos_reais.py` — for every image file in `frontend/public/produtos/` (`.jpg`/`.jpeg`/`.png`/`.webp`, case-insensitive), creates one `Produto` with:

Apostrophes are left as-is, not treated as a separator.   - Idempotent: looked up by `imagem_url` (a 1:1, deterministic key back to the source file) via `get_or_create`, so re-running the command after adding more images to the folder only creates `Produto`s for the new files, never duplicates existing ones — confirmed by running it twice in a row (115 created, then 0 created / 115 skipped on the second run).
  - Run once against the dev DB on 08/08: 115 image files found, 115 `Produto` rows created (`Produto.objects.count()` went from 1 — just `"ADS COLOR"`, the preserved test row above — to 116). **Full manual cleanup still needed for every one of these 116 rows: real `preco`, `categoria`, `marca`, and at least one `Variacao` per product, all via the Django Admin** — this command only gets a real photo and a legible name into the system, nothing else.
- **Pedido** → has many **ItemPedido** (CASCADE), belongs to **User** via `usuario` FK (PROTECT — can't delete a user with existing orders), and optionally references **Endereco** via `endereco` FK (PROTECT, `null=True, blank=True` — a shipping address is required at checkout in practice, but the FK itself is optional so pre-existing `Pedido` rows from before this field existed remain valid; `PROTECT` because an order's shipping address must never disappear from its history, even if the underlying `Endereco` is later edited or deleted — see `EnderecoViewSet` below for the corresponding delete-blocking behavior)
- **Pedido** also carries `frete_valor` (`DecimalField`), `frete_nome`/`frete_transportadora` (`CharField`), and `frete_prazo_dias` (`IntegerField`) — added 29/07 (migration `0010_pedido_frete_nome_pedido_frete_prazo_dias_and_more`) to close the "SuperFrete quote isn't persisted anywhere" gap noted under "SuperFrete Shipping Integration" below. All four are `null=True, blank=True` and, like `ItemPedido.preco_unitario`/`produto_nome`, a **snapshot frozen once at order creation** — never recalculated later, even if a fresh SuperFrete quote for the same route/weight would come back different. `null=True` rather than backfilled: pedidos placed before this field existed (including every one that used the old fixed `FRETE_PLACEHOLDER`) have no real quote to record, and guessing one from the current SuperFrete API would fabricate history exactly like the incident that `produto_nome`/`produto_tamanho` were fixed for (see below) — they simply show no freight section instead. **`Pedido.total` now includes `frete_valor`** (treated as 0 when `None`) instead of being items-only — see `signals.py::recalcula_total_pedido()` below for the implementation and the "SuperFrete Shipping Integration" section for the reasoning: it's meant to be the actual amount charged to the customer, and pedidos with no freight (all pre-29/07 rows) see no change in their `total` at all, since `frete_valor=None` contributes 0. `Pedido` also carries `link_pagamento_url` (`URLField(null=True, blank=True)`, added 07/08, migration `0011_pedido_link_pagamento_url`) — a cache of the InfinitePay checkout link already generated for this order, letting `PedidoViewSet.gerar_link_pagamento()` reuse it on a repeat call instead of minting a new one every time; see "InfinitePay Payment Integration" below for the full idempotency fix this closed.
- **ItemPedido** → references **Variacao** (PROTECT — can't delete sold variants); `subtotal` is persisted on the model (not computed on the fly). `produto_nome`/`produto_tamanho` are also persisted, as a snapshot frozen once at creation — not derived from `variacao.produto.nome`/`variacao.tamanho` on every read — for the same reason `preco_unitario` already was: `Variacao.produto`/`Variacao.tamanho` can be edited later, and a derived value would silently rewrite how a past sale is displayed whenever that happens (see the fixed quirk below for the real incident that caused, and the "Django Admin" section for the corresponding admin lockdown on `Variacao`)
- **Variacao** has `unique_together = ["produto", "tamanho"]`; also carries `peso` (kg, `DecimalField(max_digits=5, decimal_places=3)`) and `altura`/`largura`/`comprimento` (cm, `IntegerField`) — added 27/07 for the future SuperFrete shipping-cost integration (see "Not yet done" below), not consumed by anything yet. Deliberately per-`Variacao`, not per-`Produto`: confirmed as the market-standard approach (Nuvemshop, Shopify both do this) — a product's different sizes can legitimately weigh/measure differently, even though in practice many will end up with similar values. `altura`/`largura`/`comprimento` are `IntegerField`, not `DecimalField`, matching how shipping carriers (Correios/Melhor Envio/SuperFrete) normally declare package dimensions — whole cm, no real need for sub-centimeter precision; `peso` uses 3 decimal places since grams do meaningfully affect a shipping quote. All four have a `default` rather than `null=True`: a shipping calculation always needs *some* value, so an approximate default beats a missing one. Defaults (`peso=0.3`, `altura=3`, `largura=25`, `comprimento=35`) are a placeholder for a typical folded-garment envelope/package — not real per-product measurements, which the client hasn't provided yet; the migration (`produtos/migrations/0009_variacao_altura_variacao_comprimento_and_more`) applied these same defaults to every pre-existing `Variacao` row, so today every variant in the catalog reports the identical placeholder until corrected by hand. `VariacaoSerializer` exposes all four as ordinary writable fields (not `read_only` — unlike `ItemPedido.preco_unitario`, these are real data meant to be corrected once known, not something the backend derives) and both `VariacaoAdmin` and `VariacaoInline` (on `ProdutoAdmin`) expose them as editable — the likely path for filling in real values, but deliberately *not* added to `VariacaoAdmin.list_editable` alongside `estoque`: `estoque` is a live operational number that changes with every sale/restock and benefits from a fast, no-page-load edit from the changelist, while weight/dimensions are physical measurements set once and rarely revisited, better suited to the full change form (all four together, with labels) than a cramped list-view cell. **Possible future improvement, not implemented now:** if manually setting these per `Variacao` turns out to be too repetitive in practice (e.g. most sizes of most products really do share the same weight/dimensions), a natural next step would be letting a `Variacao` inherit a default from its "root" `Produto` and only override when a specific size genuinely differs — not built now since the per-`Variacao` values don't exist yet to observe that pattern from.
- **Endereco** → belongs to **User** via `usuario` FK (CASCADE — deleting a user deletes their addresses); referenced by **Pedido** via `endereco` (PROTECT — see above), so deleting an `Endereco` that's linked to any order fails until that quirk is addressed (see below)

### Business Logic via Signals

`pedidos/signals.py` contains one `pre_save` and three `post_save`/`post_delete` signals registered in `pedidos/apps.py`, all wrapped in `@transaction.atomic`:

1. **calcula_subtotal** (`pre_save`) — On ItemPedido save: sets `subtotal = quantidade × preco_unitario` before it's persisted.
2. **diminui_estoque** (`post_save`) — On ItemPedido creation: re-checks stock availability against a `select_for_update()`-locked read, then decrements Variacao.estoque via an atomic conditional `.update(estoque=F("estoque") - quantidade)` — not a plain Python read-modify-write — so a lost race between concurrent requests can't silently oversell (see the fixed concurrent-request-race quirk further down for the full story, including why `select_for_update()` alone isn't enough on this project's SQLite dev DB). Kept as a defense-in-depth backstop (e.g. for the Django admin's `ItemPedidoInline`, which doesn't go through `ItemPedidoViewSet`), since the authoritative check now lives in `ItemPedidoViewSet.perform_create()` (see below and the fixed quirks further down).
3. **atualiza_total_pedido** (`post_save`) — On ItemPedido save: recalculates Pedido.total via the shared `recalcula_total_pedido()` helper (added 29/07) as sum of ItemPedido.subtotal **plus `Pedido.frete_valor`** (treated as 0 when unset).
4. **atualiza_total_ao_deletar** (`post_delete`) — On ItemPedido delete: recalculates Pedido.total the same way, via the same helper.

`recalcula_total_pedido(pedido)` (`pedidos/signals.py`) is also called directly (not via a signal) at the end of `PedidoViewSet.perform_create()`. It's always redundant there today — `itens_criacao` is now required and non-empty on every create (see "Backend quirks" below, 30/07), so at least one `ItemPedido` post_save signal always fires and already recalculates `total` — but it's kept anyway as a cheap, idempotent safety net; it was originally added for the case of a `Pedido` created with a `frete_selecionado` but no items, a state that's no longer reachable through this endpoint.

### Authentication & Authorization

- JWT via `djangorestframework-simplejwt`, delivered as **httpOnly cookies** rather than `Authorization: Bearer` headers
  - `core/views.py::ThrottledTokenObtainPairView` (`POST /api/token/`, throttled `throttle_scope = "login"`) sets `access_token` (`Path=/`) and `refresh_token` (`Path=/api/token/refresh/`) cookies from the simplejwt response and strips them out of the JSON body; it also calls `get_token(request)` so a readable `csrftoken` cookie is issued at login
  - `core/views.py::CookieTokenRefreshView` (`POST /api/token/refresh/`) reads `refresh_token` from `request.COOKIES`, builds simplejwt's serializer directly via `self.get_serializer(data={"refresh": refresh_token})` (avoiding the private `request._full_data` attribute), and re-sets the rotated cookies from `serializer.validated_data`
  - `core/views.py::LogoutView` (`POST /api/logout/`, `IsAuthenticated`) clears both cookies via `response.delete_cookie()` using matching paths
  - `core/authentication.py::CookieJWTAuthentication` (registered as the sole `DEFAULT_AUTHENTICATION_CLASSES`) reads the JWT from `request.COOKIES.get("access_token")` instead of the `Authorization` header, and enforces CSRF (mirroring DRF's `SessionAuthentication.enforce_csrf`) on every authenticated request — the browser sends the JWT cookie automatically, so all state-changing requests (checkout, order creation, admin writes, logout) require a valid `X-CSRFToken` header matching the `csrftoken` cookie
  - Cookies use `secure=not settings.DEBUG` and `samesite="Lax"`; `CORS_ALLOW_CREDENTIALS = True` and `CSRF_TRUSTED_ORIGINS` (env var, defaults to `http://localhost:5173`) are required for the cross-origin Vite frontend to send/receive them
- Default permission: `IsAuthenticated` (all endpoints require the cookie-based token)
- `produtos` ViewSets (Categoria, Marca, Produto, Variacao) use `IsAdminOrReadOnly` (`produtos/permissions.py`) — reads are public, writes require `request.user.is_staff`
- `PedidoViewSet` uses `IsAuthenticated` + `IsDonorOrStaff` (`pedidos/permissions.py`) and filters `get_queryset()` so non-staff users only see their own orders (staff see all); `perform_create()` auto-assigns `usuario` from `request.user`, so clients never submit it. `perform_create()` also rejects (403) a non-staff request that tries to link an `endereco` id belonging to a different user — same shape of check as `ItemPedidoViewSet` below, added alongside the `Pedido.endereco` FK precisely to avoid opening a new IDOR the moment the field became client-writable (a malicious `POST /pedidos/` could otherwise link someone else's saved address to your own order, leaking that it exists/its contents via `endereco_detalhe` on every future read of the order). `perform_create()` requires a non-empty `itens_criacao` list (400 with `{"detail": "Um pedido precisa ter pelo menos um item."}` if it's missing or `[]`, checked before anything is created — see "Backend quirks" below, 30/07) and, when present, creates the `Pedido` and every `ItemPedido` line together inside one `transaction.atomic()` block — see the fixed "order creation isn't atomic" quirk below for the full design. `perform_create()` also accepts an optional `frete_selecionado` object (added 29/07, same write-only-companion-field shape as `itens_criacao`, see `FreteSelecionadoSerializer` in `pedidos/serializers.py`) and, when present, freezes its `nome`/`transportadora`/`preco`/`prazo_dias` onto the new `Pedido`'s `frete_valor`/`frete_nome`/`frete_transportadora`/`frete_prazo_dias` columns via explicit `serializer.save(...)` kwargs — same pattern `ItemPedidoViewSet.perform_create()` already uses for `preco_unitario`/`produto_nome`. `frete_valor`/`frete_nome`/`frete_transportadora`/`frete_prazo_dias` are `read_only` on `PedidoSerializer` for the same reason: always backend-set from `frete_selecionado`, never directly writable by the client. `usuario` is `read_only` on `PedidoSerializer`, and `perform_update()` replicates the `endereco`-ownership check above (against the Pedido's existing owner, not the requester) and re-asserts that owner on save — closes a real IDOR that let a Pedido's own owner reassign it (or its `endereco`) via `PUT`/`PATCH`, fixed 27/07, see the quirk entry below for the full story
- `EnderecoViewSet` uses `IsAuthenticated` + `IsDonorOrStaff`, filters `get_queryset()` by `usuario=request.user` (staff see all), and `perform_create()` forces `usuario=request.user` — closes an IDOR that let any authenticated user read/edit/delete another user's address. `usuario` is also `read_only` on `EnderecoSerializer` (root-cause fix, see below), and `perform_update()` explicitly re-asserts `serializer.instance.usuario` on save — belt-and-suspenders against a `PUT`/`PATCH` payload trying to reassign an address to a different user's id; deliberately uses the *existing* owner rather than `self.request.user`, since a staff edit of someone else's address must not silently reassign it to the staff member. `perform_destroy()` catches `django.db.models.deletion.ProtectedError` (raised when the address is still linked to a `Pedido` via the `PROTECT` FK) and re-raises it as a DRF `ValidationError` (`{"detail": "Este endereço não pode ser excluído porque está vinculado a um ou mais pedidos."}`, 400) — see the fixed quirk below
- `ItemPedidoViewSet` uses `IsAuthenticated` + `IsItemDonorOrStaff` (`pedidos/permissions.py`), filters `get_queryset()` by `pedido__usuario=request.user` (staff see all); `perform_create()` raises `PermissionDenied` (403) if a non-staff user targets a `Pedido` they don't own, and always sets `preco_unitario` server-side from `variacao.produto.preco` — the field is `read_only` on `ItemPedidoSerializer`, so clients can't forge a price or attach items to someone else's order. `perform_create()` also raises a DRF `ValidationError` (`{"detail": "Estoque insuficiente. Restam apenas N unidades."}`, 400) if `quantidade` exceeds `variacao.estoque`, checked *before* `serializer.save()` (both inside one `transaction.atomic()` block, re-fetching the `Variacao` via `select_for_update()`) — see the fixed quirks below for why the check lives here rather than only in the `diminui_estoque` signal, and for the concurrent-request race this locking (plus an atomic conditional update in the signal) closes
- `/api/registro/` uses `AllowAny`
- `usuarios/views.py::MeView` (`GET /api/me/`, `IsAuthenticated`) returns the current user via `MeSerializer` (id, username, email, is_staff) — used by the frontend to hydrate/validate the session on load and after login
- Token endpoints: `POST /api/token/` (obtain, throttled), `POST /api/token/refresh/` (refresh), `POST /api/logout/` (clears cookies, requires auth)

### Rate Limiting

- `DEFAULT_THROTTLE_CLASSES` = `ScopedRateThrottle`; only views with a `throttle_scope` attribute are throttled, so the rest of the API is unaffected
- `/api/token/` (`core/views.py::ThrottledTokenObtainPairView`, `throttle_scope = "login"`) and `/api/registro/` (`throttle_scope = "registro"`) are limited to 5 requests/min per client via `DEFAULT_THROTTLE_RATES` in `core/settings.py`
- `/api/frete/calcular/` (`throttle_scope = "frete"`) is limited to 20 requests/min — see "SuperFrete Shipping Integration" below for why this endpoint is both public and throttled, same shape as `/api/token/`/`/api/registro/`

### SuperFrete Shipping Integration

Added 27/07 — replaces the fixed `FRETE_PLACEHOLDER` (R$20) `Checkout.jsx` used to show with a real shipping quote from the [SuperFrete](https://superfrete.com/) API.

- **Environment variables** (`core/settings.py`): `SUPERFRETE_TOKEN` (the account's API token — sandbox in dev, would need swapping for a production token before a real deploy) and `SUPERFRETE_CEP_ORIGEM` (the store's own shipping-origin CEP, `"72017212"` — no hyphen, confirmed as the format the API actually accepts by calling it directly, not assumed from the docs, which don't show a full example). `SUPERFRETE_BASE_URL` isn't its own env var — same pattern as `CORS_ALLOW_ALL_ORIGINS` above, it's derived from `DEBUG` (`https://sandbox.superfrete.com` in dev, `https://api.superfrete.com` in prod), since sandbox and production use different *hosts*, not just different paths, and the sandbox token in `.env` today wouldn't work against the production host anyway — the two already have to be swapped together by hand when deploying.
- **`pedidos/services/superfrete.py`** — a plain, DRF-independent HTTP client (new `pedidos/services/` package; `requests` added to `requirements.txt`, the project's first external HTTP dependency). `calcular_frete(cep_destino, produtos)` builds and sends the `POST {SUPERFRETE_BASE_URL}/api/v0/calculator` request and returns a simplified list of shipping options. The request/response shapes below were confirmed by calling the real sandbox via curl while building this — the official docs (`superfrete.readme.io`) don't show a complete response example, and the one *request* example they do show (`options.insurance_value` as a single shipment-level value, not per product) differs from a payload shape this task was initially given to use (`insurance_value` per product) — the version actually implemented is the one confirmed to work against the real API, not the assumed one.
  - Request: `{"from": {"postal_code": "<origin>"}, "to": {"postal_code": "<8-digit destination>"}, "services": "1,2,17", "options": {"own_hand": false, "receipt": false, "insurance_value": <sum of line totals>, "use_insurance_value": true}, "products": [{"quantity", "height", "length", "width", "weight"}, ...]}` — `services` is PAC/SEDEX/Mini Envios, the three Correios-based services enabled on this account; SuperFrete silently omits any service that doesn't apply (e.g. too heavy for Mini Envios) rather than erroring, so it's safe to always request all three. `insurance_value` is a *single* total for the whole shipment (summed in Python from each line's `variacao.produto.preco × quantidade`), not per product — confirmed by testing both shapes against the sandbox.
  - Response (200): a JSON array, one entry per shipping option, each with `id`, `name` (e.g. `"PAC"`), `price` (number), `delivery_time` (business days, number), and `company.name` (carrier) among other fields not used here (`packages`, `delivery_range`, `discount`, ...). `calcular_frete()` maps this down to `{"id", "nome", "transportadora", "preco", "prazo_dias"}` per option, dropping any entry with `has_error: true`.
  - **Error handling — three real, curl-confirmed cases, deliberately not collapsed into one generic failure:** a small `SuperFreteError` exception hierarchy (`SuperFreteConfiguracaoError`, `SuperFreteDestinoInvalidoError`, `SuperFreteIndisponivelError`) lets `FreteCalcularView` (`pedidos/views.py`) respond differently depending on *whose* problem it is. A bad/expired token returns `401` with `{"message": "Token inválida!", "error": "Token inválida!"}` — classified as `SuperFreteConfiguracaoError`, our fault, never described to the client (would leak that our credentials are broken); mapped to a generic `503`. A bad/unserviceable destination CEP returns `400` with `{"errors": {"correios.destination_postcode": [...], "ms-freight-calculator.no_result": [...]}, "message": "..."}` — classified as `SuperFreteDestinoInvalidoError` by checking for those specific error keys, since a `400` can also mean something else went wrong on *our* side (e.g. malformed dimensions); this one *is* safe to tell the client, since it's actionable (try a different CEP) — mapped to a clean `400`. Anything else (network failure, timeout, unexpected response shape, any other non-`200`) is `SuperFreteIndisponivelError`, also mapped to `503`. The raw exception message (which may include SuperFrete's own response body) is only ever logged (`logger.error`/`logger.info` in the view), never put in a response body.
- **`POST /api/frete/calcular/`** (`pedidos/views.py::FreteCalcularView`, `pedidos/urls.py`) — not a CRUD resource, so it isn't registered on `pedidos/urls.py`'s router like the `ViewSet`s; a plain `path()` entry instead, same pattern as `usuarios/urls.py`'s `MeView`/`RegisterView`. Input (`pedidos/serializers.py::FreteCalcularSerializer`): `{"cep_destino": "...", "itens": [{"variacao": <id>, "quantidade": <int>}, ...]}` — deliberately a separate serializer from `ItemPedidoCriacaoSerializer` despite the identical `{variacao, quantidade}` shape today, since the two are conceptually unrelated (one creates a real `ItemPedido`, this one never persists anything) and shouldn't be coupled just because they happen to match right now. The view resolves each `variacao` id to its `Variacao` row (weight/dimensions — see the fix documented under "Key Model Relationships" — and `produto.preco`) and calls `calcular_frete()`.
  - **`AllowAny`, not the project's default `IsAuthenticated`** — deliberate, matching `/api/token/`/`/api/registro/`. Shipping cost needs to be visible before a visitor logs in, since `Carrinho.jsx` (where a customer would naturally want to see it) is itself a public route; the endpoint also doesn't read or write anything user-specific — only `Variacao` data that's already public via `GET /api/produtos/`. The real risk of being public is abuse of a *paid-adjacent* external dependency (every call is a real request against SuperFrete using this account's token/quota), so it's throttled the same way `/api/token/`/`/api/registro/` already are for the same reason — `throttle_scope = "frete"`, `20/min` (see "Rate Limiting" above).

Frontend (`Checkout.jsx`) side of this integration:

- **CEP is reused from the address, not asked for separately** — `Checkout.jsx` already collects a `cep` on every address (`enderecoSchema`) and every saved `Endereco` already has one, so the destination CEP for a freight quote is just `endereco.cep` (for a reused address) or the live value of the address form's own `cep` field (for a new one, via `useWatch({ control, name: "cep" })` — not `watch()`, the method `useForm()` itself returns: the React Compiler can't safely memoize around that one, confirmed via `npm run lint` flagging a `react-hooks/incompatible-library` warning that `useWatch` doesn't trigger). No separate "shipping CEP" field was added.
- **Recalculates automatically, not on a button press** — a `useEffect` re-quotes whenever the effective destination CEP becomes a complete 8-digit value (stripped of any hyphen) or the cart's items change. Loading/result state uses the same `{chave, ...}`-keyed-result pattern as `MeusPedidos.jsx`/`Catalogo.jsx` (see below) instead of a separate `setLoading(true)` inside the effect, for the same lint-rule reason documented there.
- **A failed/unavailable quote does not block checkout** — deliberate choice, explained inline in `Checkout.jsx`: SuperFrete is a third-party dependency, and hard-blocking every checkout whenever it hiccups would cost more (a lost sale) than accepting the order and sorting out shipping manually afterward for the rare failure case. The "Frete" section shows the backend's own error message (already precise, per the three-case classification above) alongside a note that the order can still be placed; "Confirmar pedido" is only disabled while a quote is actively in flight (`freteCalculando`), never just because the last attempt failed. When multiple options are returned (typically PAC and SEDEX), they're shown as a radio list — same visual pattern as the address selector above it — pre-selected on the cheapest, and the chosen option's price feeds the order total shown on this page. **Fixed 2026-07-29 — now persisted on the `Pedido` itself, closing the gap noted here previously:** `criarPedido()` (`src/api/pedidos.js`) gained a `frete` param, sent as `frete_selecionado` in the `POST /pedidos/` payload — the same option object this page already holds as `freteEscolhido`, unmodified. `Checkout.jsx` passes `freteEscolhido` through as-is (`undefined` when no option is currently selected — quote still loading, failed, or returned no options — in which case the Pedido is simply created with no freight snapshot, consistent with "a failed/unavailable quote does not block checkout" above). See the `Pedido.frete_valor`/`frete_nome`/`frete_transportadora`/`frete_prazo_dias` fields under "Key Model Relationships" and `PedidoViewSet.perform_create()` under "Authentication & Authorization" for the backend side, and `PedidoDetalhe.jsx` below for where it's displayed after the fact. `Pedido.total` now includes `frete_valor` (see `recalcula_total_pedido()` under "Business Logic via Signals") — the total shown on this page (`totalValor + freteValor`, computed client-side) and the `Pedido.total` the backend returns are now the same number, not just visually similar.

### InfinitePay Payment Integration

Added 03/08 — replaces the old "create the Pedido, then go straight to `/pedido-confirmado` with no real payment" flow with a real payment step via the [InfinitePay](https://www.infinitepay.io/) checkout-link API. Confirmed against the real API via curl while building this (using the dev/test handle below, the developer's own personal account) — see the exact requests/responses in the entries below; the API has no separate sandbox host or per-request auth token (unlike SuperFrete), so "testing against the real API" and "testing against what production will use" are the same thing here, modulo swapping the handle.

**Open risk, not just a footnote — read before relying on this in production:** everything about *generating* a payment link was verified against the real InfinitePay API end to end. The webhook side is different: its *logic* (routing, forged-payload rejection, idempotency — all the code paths described below) was verified by simulating requests against this project's own dev server, but the actual delivery path — a real customer paying, and InfinitePay's own servers successfully reaching a publicly-hosted `BACKEND_URL` with a genuine webhook call — has never been exercised, because nothing in this dev environment is publicly reachable from the internet. This is not a "nice to do eventually" item: until it's tested against a real completed payment (via a tunnel like ngrok, or once there's a real deploy — see "Not fully testable end-to-end in this environment" below), there is no direct evidence that InfinitePay can actually reach this endpoint at all — a firewall rule, a misconfigured `BACKEND_URL`, or some other delivery failure InfinitePay's side would go unnoticed until a real order gets stuck showing `"novo"` after a customer has genuinely paid. Treat that path as unverified, not just "not yet tried."

- **Environment variables** (`core/settings.py`): `INFINITEPAY_HANDLE` — the receiving account's public handle (e.g. `"renato-ramos-0g5"`, today the developer's personal dev/test account; must be swapped for the client's real handle before production). `FRONTEND_URL`/`BACKEND_URL` — new to this project (nothing before this needed the backend to know its own public URL or the frontend's), used to build `redirect_url`/`webhook_url` below; default to the local dev addresses (`localhost:5173`/`localhost:8000`), both need real values in production. No `INFINITEPAY_BASE_URL` split by `DEBUG` the way `SUPERFRETE_BASE_URL` is — confirmed via curl that InfinitePay's API doesn't distinguish sandbox/production by host, or require any token/API key per request at all: knowing a valid `handle` (a public identifier, not a secret — it's the same string that appears in the checkout URL itself) is enough for anyone to generate a checkout link that pays into that account. That statelessness is also why there's no "our credentials expired" failure mode analogous to SuperFrete's — see the error handling below.
- **`pedidos/services/infinitepay.py`** — same shape as `pedidos/services/superfrete.py` (plain, DRF-independent HTTP client, no sandbox distinction needed so no settings-derived base URL). Two functions:
  - `criar_link_pagamento(order_nsu, itens, redirect_url, webhook_url)` — `POST https://api.checkout.infinitepay.io/links` with `{"handle", "order_nsu", "redirect_url", "webhook_url", "items": [{"quantity", "price", "description"}, ...]}`, `price` in cents **per unit** (confirmed via curl: a `{quantity: 3, price: 500}` line produces a different link than `{quantity: 1, price: 1500}`, even though both total R$15,00 — the two aren't interchangeable). Returns the checkout URL from the `{"url": "..."}` response. Errors: an unrecognized `handle` returns `422` with `{"success": false, "message": "Unable to create checkout link"}` (confirmed via curl with a deliberately bogus handle) — classified as `InfinitePayConfiguracaoError`, our fault, never described to the client. Any other non-200 (malformed payload — always a bug on our side here, since every field is server-generated from the Pedido, never taken from client input the way SuperFrete's destination CEP is; network failure; unexpected response shape) is `InfinitePayIndisponivelError`. Unlike SuperFrete's three-way split, there's no "safe to relay to the client" case at all in this client — both exception classes map to the same generic `503` in the view, kept as separate classes purely for clearer logging.
  - `verificar_pagamento(order_nsu, transaction_nsu, slug)` — `POST https://api.checkout.infinitepay.io/payment_check` with `{"handle", "order_nsu", "transaction_nsu", "slug"}`, returns `{"paid": bool, "amount_centavos": int | None}`. This is the function the webhook handler below actually trusts — see "Webhook" for why. Confirmed via curl that an unrecognized/fake `transaction_nsu` still returns `200` with `{"success": false}` (not a 401/403) — there's no auth on this call either, which is fine, because what it's confirming isn't "who is calling this" but "does InfinitePay's own ledger agree this specific transaction was paid."
- **Where the link is generated — a separate action, not inside `PedidoViewSet.perform_create()`:** `PedidoViewSet.gerar_link_pagamento()` (`pedidos/views.py`), a DRF `@action` at `POST /api/pedidos/{id}/gerar-link-pagamento/`, called by the frontend right after `POST /pedidos/` succeeds — two HTTP calls, not one. Considered folding InfinitePay into `perform_create()`'s existing `transaction.atomic()` block (same call site SuperFrete's quote is *not* in, notably) and rejected: order creation's transaction does real, hard-to-retry-safely work — locking `Variacao` rows, decrementing stock, freezing `preco_unitario`/`produto_nome` (see "Key Model Relationships") — and a slow or flaky InfinitePay response inside that same block would either hold a DB transaction open for the duration of an external HTTP call, or force rolling back a perfectly valid, already-decremented order just because a third-party payment gateway hiccuped. Splitting them means: the Pedido is real and stock-accurate the instant `POST /pedidos/` returns, regardless of InfinitePay's availability; a failed link-generation attempt can be retried on its own (`gerar_link_pagamento()` re-checked, no stock/serializer work repeated) without ever re-submitting the cart; and `Pedido.status` staying `"novo"` *is* the "awaiting payment" state — no new status value or model field needed for this. The action 400s if the Pedido isn't `"novo"` (already paid, or cancelled) — generating a fresh checkout link for either would be misleading (a second payment for an already-confirmed order) — and, since `get_object()` runs `IsDonorOrStaff.has_object_permission()` the same as every other detail action on this ViewSet, a non-owner request 404s (filtered out by `get_queryset()` before the permission check even runs) rather than reaching this logic at all. `order_nsu` is always `str(pedido.id)` — no new column needed on `Pedido` to remember it, since the webhook can always look the Pedido back up by primary key.
  - **Items sent include freight, not just `ItemPedido` lines:** `Pedido.total` includes `frete_valor` (see `recalcula_total_pedido()` under "Business Logic via Signals") but freight isn't an `ItemPedido` row — without an extra line for it, the amount actually charged via InfinitePay would fall short of `pedido.total` by exactly the freight value. When `frete_valor` is set, a line named after the frozen `frete_nome` snapshot (e.g. `"Frete (PAC)"`) is appended with `preco_centavos = int(pedido.frete_valor * 100)`. Verified via a real curl-confirmed call against a real Pedido (id 136, one item R$1.500,00 + frete R$35,66 = R$1.535,66) that the generated link's items sum to exactly `pedido.total` in cents (153566), and that the link itself resolves (`200`) when fetched.
  - `redirect_url` is `{FRONTEND_URL}/pedido-confirmado?pedidoId={id}` — a query param, not React Router `state`, because the customer is about to leave the SPA entirely for InfinitePay's own hosted checkout page; whatever comes back is a brand-new browser navigation with no access to this session's in-memory state (see `PedidoConfirmado.jsx` below). `webhook_url` is `{BACKEND_URL}/api/pedidos/webhook-infinitepay/`.
- **Fixed 2026-08-07 — no idempotency on link generation, previously a real, unmitigated gap.** `gerar_link_pagamento()` could legitimately be called more than once for the same `Pedido` — the frontend's own "Tentar novamente" retry button (`Checkout.jsx`, see below) re-calls it with the same `pedidoCriadoId` on a failed attempt, and nothing stopped a client from calling it again on a *successful* prior attempt either. Every call independently created a brand-new InfinitePay checkout link via `POST /links`, with no check for a still-valid link already existing for this `Pedido` — meaning multiple distinct, simultaneously valid checkout links could exist for the same order, and since `payment_check`/the webhook only confirm that *some* transaction for that `order_nsu` was paid the expected amount (not that only one payment ever happens), more than one of those links actually getting paid (double-click, a leaked/reused old link, a webhook retry racing a second manual payment) would go financially unnoticed by this codebase — `Pedido.status` only flips once, but each payment still completes for real on InfinitePay's side, discoverable only by reconciling against InfinitePay's own dashboard. **Re-confirmed before fixing, not assumed: no expiration or invalidation mechanism for a checkout link is documented by InfinitePay.** Checked both places named in the original note — the technical API reference (`docs.infinitepay.io`, and the same host `api.checkout.infinitepay.io/docs` and `api.infinitepay.io/docs` both 301-redirect to) could not actually be reached (`getaddrinfo ENOTFOUND`, consistent across many retries and several guessed paths — the domain simply doesn't resolve from this environment right now, not a 404 or an auth wall) — and the Central de Ajuda (consumer help center), which *was* reachable: searched directly for link expiration/cancellation and read the two main articles on using Link de Pagamento ("Como usar o Link de Pagamento?", "Como fazer uma venda com o Link de Pagamento?") plus a search for "cancelar cobrança" — none mention automatic expiration, and the only link-management feature described (`Histórico` under the `Vender` menu) is explicitly read-only consultation of past links, not cancellation/deactivation. Not a hard proof at the API level (the technical reference genuinely couldn't be reached this pass), but consistent with, and no weaker than, the original unresearched assumption — and the product itself exposing no such concept to end users is real evidence against a hidden API-level one. **Fix:** new `Pedido.link_pagamento_url` column (`URLField(null=True, blank=True)`, migration `0011_pedido_link_pagamento_url`, `pedidos/models.py`) caches the checkout URL InfinitePay returns. `gerar_link_pagamento()` (`pedidos/views.py`) now checks it immediately after the existing `status != "novo"` guard: if already set, returns it directly (`Response({"url": pedido.link_pagamento_url})`) with **no call to `criar_link_pagamento()`/InfinitePay at all**; otherwise the flow is unchanged, and the URL is persisted (`pedido.link_pagamento_url = url; pedido.save(update_fields=["link_pagamento_url"])`) right before returning it for the first time. **Validity is tied to `Pedido.status`, deliberately not to time** — no new expiration/expiry-date field: the existing `status != "novo"` guard already blocks generating (or now, reusing) a link the moment the order leaves `"novo"` (paid or cancelled), which is exactly when a cached link stops being relevant; nothing about the fix needed to know when a link itself expires, since InfinitePay was reconfirmed above to document no such thing. Same pattern as `frete_valor`/`frete_nome` etc: `null=True, blank=True`, no backfill for pre-existing `Pedido` rows (they simply generate and cache a link on first real call, same as any row created after this fix). `PedidoAdmin.readonly_fields` (`pedidos/admin.py`) now also includes `link_pagamento_url`, unconditionally (not gated by `obj is not None` like `usuario`/`endereco`/the `frete_*` fields) — unlike those, there's no legitimate reason for a staff member to ever hand-type a payment link, on a new `Pedido` or an existing one, so there's no add-time use case to preserve; safe unconditionally the same way `total` already is, since the field is nullable with no default. **This does not address the two other, separate gaps already on record for this integration** (see the callouts at the top of this section and under "Webhook" below): the webhook's real end-to-end delivery path is still unverified, and `INFINITEPAY_HANDLE` still points at the developer's personal dev/test account — neither was in scope here. **Verified via curl against the real InfinitePay API, not mocked** (three consecutive `POST /pedidos/141/gerar-link-pagamento/` calls, logged in as the order's own owner): the first call took 0.53s (a real network round trip to InfinitePay's `POST /links`) and returned a real, working checkout URL (separately confirmed to resolve `200` when fetched); the second and third calls took 0.03s and 0.02s respectively — no InfinitePay round-trip, consistent with hitting the DB cache instead — and returned the *exact same* URL string as the first call, byte for byte; a direct DB read after confirmed `Pedido.link_pagamento_url` held that same URL. Separately verified the status guard still works even with a link already cached: manually flipped the same Pedido's `status` to `"confirmado"` (bypassing the API, since there's no legitimate way to reach that state without a real completed payment) and confirmed `POST .../gerar-link-pagamento/` still returned a clean `400` with `{"detail": "Este pedido não está aguardando pagamento."}`, unchanged from before this fix — the cached URL does not bypass the guard. Test Pedido's `status`/`link_pagamento_url` were reset back to `"novo"`/`None` afterward to leave dev data as found.
- **Webhook — `POST /api/pedidos/webhook-infinitepay/`** (`pedidos/views.py::InfinitePayWebhookView`, `pedidos/urls.py`) — not a CRUD resource, a plain `path()` entry like `FreteCalcularView`, but registered **before** `router.urls` in `urlpatterns`, not after: `DefaultRouter`'s own `pedidos/<pk>/` detail route uses a permissive `pk` regex (`[^/.]+`) that would otherwise match `pedidos/webhook-infinitepay/` first (with `pk="webhook-infinitepay"`) if the router's patterns were listed first, since Django's resolver stops at the first pattern that matches and tries `urlpatterns` in order — confirmed via `resolve("/api/pedidos/webhook-infinitepay/")` in a shell before settling on this ordering, catching what would otherwise have been a silent routing bug (the webhook URL would 404 via the ViewSet's `retrieve()`, having never reached `InfinitePayWebhookView` at all).
  - **⚠ Not fully testable end-to-end in this environment — see the callout at the top of this section.** The link-generation side (`criar_link_pagamento`, the `gerar-link-pagamento` action, including ownership/status checks) was verified against the real InfinitePay API and the real dev server end-to-end, cookies and CSRF included. The webhook handler's *logic* (routing, malformed-payload handling, idempotency, and — critically — that a forged "payment succeeded" claim is rejected) was also verified against the real running server. What could **not** be verified is the full real-world path of an actual customer paying and InfinitePay's servers delivering a genuine webhook to a publicly reachable `BACKEND_URL` — that needs a real completed payment and a publicly reachable dev tunnel (e.g. ngrok), neither of which was set up for this pass. **This is a real gap, not a formality:** confirm it works — a test payment through a tunnel, or a smoke test right after the first production deploy — before trusting this flow to confirm real orders unattended.
  - **No signature/HMAC/secret of any kind — confirmed by reading InfinitePay's own docs, not assumed.** Every other public/`AllowAny` endpoint in this project (`FreteCalcularView`, `/api/token/`, `/api/registro/`) is public because *authentication* genuinely doesn't apply (no user session exists yet, or the data itself is public) — this one is different: it's public because the caller (InfinitePay's server) can't present our cookie-based JWT, but the *payload* claims something security-sensitive ("this order was paid"), and there is nothing in the request — no header, no signature, no shared secret — that proves it actually came from InfinitePay and wasn't forged by anyone who discovers the URL.
  - **The actual trust mechanism: `verificar_pagamento()`, not the webhook body.** The view never marks a `Pedido` `"confirmado"` based on the webhook payload's own claims (`amount`, `paid_amount`, etc). Instead, it takes only the *identifiers* the webhook provided (`order_nsu`, `transaction_nsu`, `invoice_slug`) and calls InfinitePay's own `payment_check` API back, independently, asking whether that specific transaction is really paid. A forged webhook naming a `transaction_nsu` that doesn't exist (or was never paid) gets a real `{"paid": false}` back from InfinitePay itself — confirmed via curl (both directly against the API and through a full HTTP round-trip against this project's own dev server) that a forged webhook body for a real, unpaid `Pedido` is accepted (`200`, matching InfinitePay's documented expected response shape) but leaves `Pedido.status` completely unchanged.
  - **A second, subtler forgery this also closes: paying the right `order_nsu` but the wrong amount.** Because the `handle` is public and `order_nsu` isn't bound to us by any token, anyone can generate their *own* checkout link citing an existing Pedido's id as `order_nsu` and genuinely pay it themselves — just for less than the real order total (e.g. R$0,01). `payment_check`'s response includes the actual paid amount for that specific transaction, so the view compares it against `pedido.total` (in cents) before confirming; a real-but-wrong-amount payment doesn't flip the order either. This is checked against `amount`, not the webhook's `paid_amount` — the two can legitimately differ (a card installment fee is added on top; confirmed in InfinitePay's own documented webhook example, `amount: 1000` vs `paid_amount: 1010`), and `amount` is the one that reflects what our own `items` payload actually declared when the link was created.
  - **Idempotent by design:** if `pedido.status` is already something other than `"novo"` (already confirmed, or cancelled), the view returns `{"success": true}` immediately without calling `payment_check` again — handles InfinitePay redelivering the same webhook, and avoids spending a second `payment_check` call on a Pedido that's already settled either way.
  - **Response codes, matching InfinitePay's documented contract** (`200`/`{"success": true}` = accepted; `400` = malformed, safe to retry against): a missing `order_nsu`/`transaction_nsu`, or an `order_nsu` that doesn't resolve to any `Pedido`, is `400`. A `payment_check` call that itself fails (network/InfinitePay down) is `503` — worth a retry, unlike a genuinely malformed payload. A `payment_check` that succeeds but reports "not paid" or a mismatched amount is still `200` — the webhook itself was processed correctly, it just didn't result in a confirmation, and there's nothing a retry would change about that.
  - **Throttled** (`throttle_scope = "infinitepay_webhook"`, `100/min`, `DEFAULT_THROTTLE_RATES` in `core/settings.py`) — same reasoning as `frete` (`AllowAny` + each call costs a real outbound request to a third-party API), just a higher ceiling: expected volume here is roughly one call per paid order, not one per cart-browsing visitor, but it's still a public endpoint that can't be left completely unbounded.

Frontend side of this integration:

- **`src/api/pedidos.js::gerarLinkPagamento(pedidoId)`** — `POST /pedidos/{id}/gerar-link-pagamento/`, returns the checkout URL. Kept separate from `criarPedido()`, mirroring the backend split above.
- **`Checkout.jsx`** — `handleConfirmar()` no longer navigates to `/pedido-confirmado` directly after `criarPedido()` succeeds. It now clears the cart and calls a new `solicitarLinkPagamento(pedidoId)` helper, which calls `gerarLinkPagamento()` and, on success, does a full-page navigation (`window.location.assign(url)` — not `window.location.href = url`, which the React Compiler's `react-hooks/immutability` rule flags as mutating something defined outside the component; `.assign()` isn't flagged and does the same thing, confirmed via `npm run lint`) to InfinitePay's hosted checkout. Once a Pedido has been created (tracked via a new `pedidoCriadoId` state), the page renders a dedicated "gerando link de pagamento" screen instead of either the checkout form or nothing — the earlier `if (itens.length === 0) return null` guard (the cart is already empty by this point, same as before) now also checks `!pedidoCriadoId`, so this screen doesn't disappear the instant the cart clears. If `gerarLinkPagamento()` fails, this screen shows the error and a "Tentar novamente" button that re-calls `solicitarLinkPagamento()` with the *same* `pedidoCriadoId` — no new Pedido, no re-submitted cart, matching the backend design above (a failed link generation is retryable on its own).

### Query Optimization

`ProdutoViewSet` uses `select_related("marca", "categoria").prefetch_related("variacoes")` to avoid N+1 queries, with a default `order_by("nome")` so pagination is always deterministic (avoids `UnorderedObjectListWarning`); clients can still override via the `ordering` query param (`ordering_fields`: nome, preco). Supports `filterset_fields`, `search_fields` (nome, marca__nome).

**Customizable page size, added 08/08:** `ProdutoViewSet.pagination_class` is `produtos/pagination.py::ProdutoPagination` (a thin `PageNumberPagination` subclass), not the project-wide `DEFAULT_PAGINATION_CLASS` (fixed `PAGE_SIZE = 10`, `core/settings.py`) — scoped to this one `ViewSet` rather than raising `page_size_query_param` globally, since the Catálogo is the only page with a page-size selector today; every other paginated list (`pedidos`, `enderecos`, ...) still defaults to a fixed 10. `page_size_query_param = "page_size"` lets a client request `?page_size=20`; `max_page_size = 50` caps it server-side regardless of what's requested — confirmed via curl that `?page_size=10000` still returns only 50 results, not the full 51-row dev catalog, so the query param can't be abused to force an unbounded response. Frontend: `Catalogo.jsx` adds a "10/20/50 por página" `Select` next to the existing ordering `Select`, synced to the URL via the `page_size` search param (same `useSearchParams` pattern as every other filter on this page — omitted from the URL entirely at the default value of 10, same as `atualizarFiltro` already does for `ordering`); changing it resets `page` back to 1, same as changing any other filter. `totalPaginas` is now computed from the selected `pageSize`, not a hardcoded constant. `listarProdutos()` (`src/api/produtos.js`) gained an optional `pageSize` param, sent as `page_size` only when provided.

### Mega Menu Navigation (`GET /api/menu/categorias/`)

Added 07/08. Originally backed a single catch-all "Categorias" mega menu (`MegaMenu.jsx`, since replaced — see below); as of the same-day Header redesign, backs the "Roupas" mega menu and the "Tênis"/"Acessórios" nav links inside `frontend/src/components/HeaderNav.jsx` (see "Frontend" below) instead. The endpoint itself, and its shape, are unchanged by that redesign — only which frontend component consumes it changed.

- **`produtos/views.py::CategoriaMenuView`** (`produtos/urls.py`, plain `path("menu/categorias/", ...)`, not a router registration — same "not a CRUD resource" pattern as `pedidos/views.py::FreteCalcularView`) — for every `Categoria` that has at least one `Produto`, returns the list of `Marca`s that have at least one `Produto` *in that specific `Categoria`*: `[{"id", "nome", "marcas": [{"id", "nome"}, ...]}, ...]`. A `Categoria` with zero `Produto`s doesn't appear in the response at all, and a `Marca` never appears under a `Categoria` it has no stock in — both by construction, not by a separate empty-check: the whole structure is built from one `Produto.objects.filter(categoria__isnull=False, marca__isnull=False).values(...).distinct()` query, grouped in Python, so an empty combination simply never produces a row to begin with.
- **Dedicated endpoint, not assembled client-side from the existing `GET /categorias/` + `GET /marcas/`** — considered and rejected: those two list *every* `Categoria`/`Marca` that exists, with no way to tell which combinations actually have products behind them short of also walking every `Produto`, and both endpoints (`categorias`, `marcas`, `produtos`) are paginated at 10/page — building the menu client-side would mean paging through the *entire* product catalog on every page load just to know which columns/links to show. One indexed query here does the same job in a single round trip regardless of how large the catalog grows, and keeps "don't show an empty combination" a backend guarantee instead of a frontend filtering step that every future consumer of this data would have to remember to redo.
- **`AllowAny`**, not the project's default `IsAuthenticated` — same reasoning as `ProdutoViewSet`'s read access via `IsAdminOrReadOnly`: this is catalog navigation, has to work for an anonymous visitor, and the view only ever handles `GET` (no write path to gate behind staff the way `IsAdminOrReadOnly` would). Exposes nothing that isn't already public via `GET /produtos/`. Not throttled either, for the same reason `GET /produtos/`/`GET /categorias/` aren't — it's a read against our own DB, no external/paid dependency and no abuse-worthy cost the way `/api/frete/calcular/`'s SuperFrete calls are.
- Verified via curl: response correctly omits any `Categoria`/`Marca` combination with zero matching `Produto`s; following a returned `{categoria.id, marca.id}` pair through `GET /produtos/?categoria={id}&marca={id}` (the same query the frontend's mega menu links use) returns exactly the matching product(s) — confirms the ids round-trip correctly into the existing `ProdutoViewSet.filterset_fields` filter, not just that the menu endpoint itself returns a well-shaped response.

## DRF Configuration

- Pagination: `PageNumberPagination`, 10 items per page
- Filter backends: `DjangoFilterBackend`, `SearchFilter`, `OrderingFilter`
- Auth: `core.authentication.CookieJWTAuthentication` (JWT read from the `access_token` cookie, not the `Authorization` header; enforces CSRF on authenticated requests)
- Throttling: `ScopedRateThrottle`, applied only to `/api/token/` and `/api/registro/` (5/min each)
- CORS: all origins allowed only when `DEBUG=True`; restricted to `CORS_ALLOWED_ORIGINS` in production; `CORS_ALLOW_CREDENTIALS = True` so the frontend can send/receive the auth cookies cross-origin

Backend quirks discovered while building the checkout flow — most have since been fixed at the source (dated entries below); kept as a running log rather than pruned once fixed, since the reasoning behind each fix is worth keeping. The one exception still open is the vestigial `usuario: user.id` frontend field noted below, which is harmless but not yet cleaned up:
- **Fixed 2026-07-24 — was a real IDOR, not just a quirk:** `EnderecoViewSet` didn't override `perform_update()` (only `perform_create()`), and `EnderecoSerializer` had `usuario` as a plain writable field. Since `IsDonorOrStaff`'s object-level check only confirms the caller owns (or is staff for) the address being edited — it says nothing about what *values* can be written — any authenticated user could `PUT`/`PATCH` `/api/enderecos/{id}/` on their own address with `usuario: <outro_id>` in the body and reassign that address to another user's account. This only affected direct API use (curl/Postman/etc) — the frontend never sent `usuario` on edit (see below), so the UI itself couldn't trigger it. **Fix:** `usuario` is now `read_only` on `EnderecoSerializer` (`pedidos/serializers.py`) — the root-cause fix, chosen over a model-level `blank=True`/`null=True` change because (a) it needs no migration, (b) it's semantically correct (an `Endereco` should never actually have a null owner — the model constraint should stay required), and (c) `blank=True`/`null=True` alone wouldn't have closed the vulnerability anyway, since it only affects requiredness/nullability, not writability — a still-writable field remains just as attackable. `EnderecoViewSet.perform_update()` (`pedidos/views.py`) was also added, re-asserting `serializer.instance.usuario` on every save as defense in depth (technically redundant once the field is read-only, since DRF excludes read-only fields from `validated_data` entirely, but cheap insurance if the serializer ever changes). Manually verified via curl: authenticated as user A, a `PUT` (all required fields + `usuario: <user B's id>`) and a `PATCH` (`{"usuario": <user B's id>}`) against user A's own address both returned `200` with the edit applied, but `usuario` stayed A's id in both cases. **Fixed again, 2026-07-27 — same hole, different door:** the API-level fix above never touched the Django Admin, and an audit of every `ModelAdmin` in the project (prompted by the `ItemPedido`/`Pedido` admin-integrity fixes below) found `EnderecoAdmin` (`pedidos/admin.py`) had no `readonly_fields` at all — `usuario` was a plain editable dropdown in the change form, so a staff member could reassign an `Endereco` (and its whole `Pedido` history via `Pedido.endereco`) to a different user directly through the admin, completely bypassing the `read_only`-on-the-serializer protection above, which only ever covered the API. **Fix:** `EnderecoAdmin.get_readonly_fields()` now marks `usuario` readonly *only when editing an existing `Endereco`* (`obj is not None`) — same conditional shape as `ITEM_PEDIDO_CAMPOS_CALCULADOS` (see the Django Admin section below), because `Endereco.usuario` has no default and isn't nullable (`models.ForeignKey(User, on_delete=models.CASCADE)`), so an unconditional readonly would break creating a new `Endereco` via the admin. - **Fixed 2026-07-27:** Stock decrement used to not be safe against concurrent requests for the same `Variacao`. `diminui_estoque` (`pedidos/signals.py`) checked `variacao.estoque < instance.quantidade` and then did `variacao.estoque -= instance.quantidade; variacao.save()` — a plain Python read-modify-write to an absolute value — and none of the three places that read a `Variacao` for a stock check (`ItemPedidoViewSet.perform_create()`, the `itens_criacao` loop in `PedidoViewSet.perform_create()`, and `diminui_estoque` itself) locked the row. Two different clients racing for the last unit(s) of the same `Variacao` could both read the same pre-decrement `estoque`, both pass the check, and both write an absolute new value — a lost update, silently overselling instead of the second request being rejected. **Fix, applied at all three points:** each now does `Variacao.objects.select_for_update().get(pk=...)` instead of trusting an already-resolved (unlocked) `Variacao` instance, and `diminui_estoque`'s actual decrement now uses an atomic conditional update — `Variacao.objects.filter(pk=variacao.pk, estoque__gte=quantidade).update(estoque=F("estoque") - quantidade)` — checking the returned row count, instead of computing the new value in Python and writing it back. `ItemPedidoViewSet.perform_create()` also gained a `with transaction.atomic():` wrap it didn't have before (needed regardless of locking — see below).
  - **`select_for_update()` alone is not sufficient, and this project can prove it today:** `connection.features.has_select_for_update` is `False` on SQLite (confirmed via `manage.py shell`), and Django's SQL compiler gates the *entire* `select_for_update()` code path — including the "FOR UPDATE" clause *and* the "must be inside a transaction" check it would otherwise enforce — behind that feature flag (`django/db/models/sql/compiler.py`). So on SQLite, `.select_for_update()` is a silent no-op: no lock, no error, just a plain `SELECT`, on any backend that doesn't support it. The atomic conditional `.update(estoque=F(...) - quantidade)` is the layer that's actually safe regardless of backend, since the row's current value, the `estoque__gte` condition, and the new value are all evaluated together in one SQL statement — a concurrent writer can't split "check" from "write" apart, which is exactly what the old `variacao.estoque -= quantidade; variacao.save()` pattern allowed. `select_for_update()` is kept anyway (real protection on Postgres/MySQL — the Phase 5 target — and it's what the earlier "known limitation" note singled out), but the `F()` update is the layer this project can actually rely on and verify before that migration.
  - **`ItemPedidoViewSet.perform_create()` needed a new `transaction.atomic()` wrap, not just locking:** without it, a rejection from the now-properly-checked `diminui_estoque` signal (e.g. losing a race) would arrive *after* the `ItemPedido` row's `INSERT` had already committed on its own (same root cause as the orphaned-row bug fixed in the `ValueError`→`ValidationError` entry above, just triggered by a lost race instead of a single over-quantity request) — wrapping the check and `serializer.save()` together means a rejection anywhere in that block rolls back the `INSERT` too. The `itens_criacao` loop in `PedidoViewSet.perform_create()` already had this wrap from when it was built (see the "order creation isn't atomic" fix above), so it only needed the `select_for_update()` change.
  - **No PostgreSQL available to test against** (checked: no `psql`/`postgres` binary, no Docker, no passwordless `sudo` to install it in this environment) — asked the user, who chose to proceed without it rather than install Postgres. Validation instead: (1) static review confirming every `select_for_update()` call sits inside a `transaction.atomic()` block, since Django only *enforces* that requirement on backends where `has_select_for_update` is `True` — SQLite won't raise `TransactionManagementError` even if that nesting were wrong, so this had to be checked by reading the code, not by running it; (2) the existing curl regression suite (single-item creation, insufficient-stock rejection with no orphaned row, the `itens_criacao` atomic batch, both its failure and success paths) re-run and passing unchanged; (3) a real `threading`-based concurrency test (`estoque=1`, two `POST /itens/` requests for `quantidade=1` each, fired at a `threading.Barrier` to maximize simultaneity) — expected, per SQLite's whole-database write-lock, to be inconclusive (unable to distinguish fixed from still-racy code), but turned out not to be: the *old* code's race window sat entirely outside any transaction (the pre-check read `serializer.validated_data["variacao"]`, a plain unlocked Python read, before `serializer.save()` ever opened a transaction), so SQLite's write-lock never protected it. Re-running the exact same test against the unfixed code (via `git stash`) reproduced the overselling bug directly: **2 successes out of 2 requests in 4 of 5 trials**, both writes computing `1 - 1 = 0` independently and one decrement silently vanishing. Against the fixed code, the same test ran **12 times with exactly 1 success every time** — the loser got either a clean `400` or, more often, an unrelated `OperationalError: database is locked` `500` (SQLite's dev-server write-lock timeout under genuinely concurrent threaded requests, not a bug in the fix's logic — confirmed via direct DB inspection after each run: no orphaned rows, no negative stock, no double-decrement in any trial). **What this does and doesn't prove:** it's real evidence the specific exploitable gap in the old code (an unlocked check outside any transaction) is closed, and that the atomic `F()` update behaves correctly under genuine SQLite write contention. It is *not* evidence that `select_for_update()` correctly serializes concurrent transactions under real MVCC/row-level locking, since SQLite never exercises that code path at all (confirmed above) — that guarantee rests on PostgreSQL's documented `SELECT ... FOR UPDATE` semantics plus the static code review, not on anything executable in this environment. Re-verify with an actual concurrency test against PostgreSQL before or during the Phase 5 migration.
- **Fixed 2026-07-30 — a Pedido with zero items was still creatable via `POST /pedidos/`, a leftover gap from the old flow, not a real use case:** the "order creation isn't atomic" fix (27/07, above) made `itens_criacao` optional so the pre-existing "create empty Pedido, then `POST /itens/` per line" flow would keep working unchanged during that migration.
