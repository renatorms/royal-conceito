# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Royal Conceito — an e-commerce backend for a clothing store, built with Django 6 + Django REST Framework. Brazilian Portuguese is used for model/field names and UI. The frontend (React/Vite) is under active development (Phase 4) in `frontend/`.

## Common Commands

All commands run from `backend/`:

```bash
# Activate virtualenv
source .venv/bin/activate

# Run dev server
python manage.py runserver

# Database migrations
python manage.py makemigrations
python manage.py migrate

# Run tests
python manage.py test
python manage.py test produtos    # single app

# Create admin user
python manage.py createsuperuser

# Install dependencies
pip install -r requirements.txt
```

## Architecture

**Monolithic Django project** with three apps under `backend/`:

- **core/** — Project settings, root URL config, JWT token endpoints
- **produtos/** — Product catalog (Categoria, Marca, Produto, Variacao)
- **pedidos/** — Order processing (Pedido, ItemPedido, Endereco) + business logic signals
- **usuarios/** — User registration (uses Django's built-in User model)

### Data Flow

```
HTTP Request → DRF Router → ViewSet → Serializer → Model/ORM → Signal → SQLite
```

All API endpoints use DRF's `DefaultRouter` with `ModelViewSet`. Each app registers its own router in its `urls.py`, and `core/urls.py` includes them all under `/api/`.

### Key Model Relationships

- **Produto** → has many **Variacao** (size variants with stock tracking, CASCADE)
- **Produto** → belongs to **Marca** and **Categoria** (both SET_NULL)
- **Pedido** → has many **ItemPedido** (CASCADE), belongs to **User** via `usuario` FK (PROTECT — can't delete a user with existing orders), and optionally references **Endereco** via `endereco` FK (PROTECT, `null=True, blank=True` — a shipping address is required at checkout in practice, but the FK itself is optional so pre-existing `Pedido` rows from before this field existed remain valid; `PROTECT` because an order's shipping address must never disappear from its history, even if the underlying `Endereco` is later edited or deleted — see `EnderecoViewSet` below for the corresponding delete-blocking behavior)
- **ItemPedido** → references **Variacao** (PROTECT — can't delete sold variants); `subtotal` is persisted on the model (not computed on the fly)
- **Variacao** has `unique_together = ["produto", "tamanho"]`
- **Endereco** → belongs to **User** via `usuario` FK (CASCADE — deleting a user deletes their addresses); referenced by **Pedido** via `endereco` (PROTECT — see above), so deleting an `Endereco` that's linked to any order fails until that quirk is addressed (see below)

### Business Logic via Signals

`pedidos/signals.py` contains one `pre_save` and three `post_save`/`post_delete` signals registered in `pedidos/apps.py`, all wrapped in `@transaction.atomic`:

1. **calcula_subtotal** (`pre_save`) — On ItemPedido save: sets `subtotal = quantidade × preco_unitario` before it's persisted.
2. **diminui_estoque** (`post_save`) — On ItemPedido creation: decrements Variacao.estoque. Also re-checks stock availability and raises a DRF `ValidationError` if insufficient — kept as a defense-in-depth backstop (e.g. for the Django admin's `ItemPedidoInline`, which doesn't go through `ItemPedidoViewSet`), since the authoritative check now lives in `ItemPedidoViewSet.perform_create()` (see below and the fixed quirk further down).
3. **atualiza_total_pedido** (`post_save`) — On ItemPedido save: recalculates Pedido.total as sum of ItemPedido.subtotal.
4. **atualiza_total_ao_deletar** (`post_delete`) — On ItemPedido delete: recalculates Pedido.total.

### Authentication & Authorization

- JWT via `djangorestframework-simplejwt`, delivered as **httpOnly cookies** rather than `Authorization: Bearer` headers
  - `core/views.py::ThrottledTokenObtainPairView` (`POST /api/token/`, throttled `throttle_scope = "login"`) sets `access_token` (`Path=/`) and `refresh_token` (`Path=/api/token/refresh/`) cookies from the simplejwt response and strips them out of the JSON body; it also calls `get_token(request)` so a readable `csrftoken` cookie is issued at login
  - `core/views.py::CookieTokenRefreshView` (`POST /api/token/refresh/`) reads `refresh_token` from `request.COOKIES`, builds simplejwt's serializer directly via `self.get_serializer(data={"refresh": refresh_token})` (avoiding the private `request._full_data` attribute), and re-sets the rotated cookies from `serializer.validated_data`
  - `core/views.py::LogoutView` (`POST /api/logout/`, `IsAuthenticated`) clears both cookies via `response.delete_cookie()` using matching paths
  - `core/authentication.py::CookieJWTAuthentication` (registered as the sole `DEFAULT_AUTHENTICATION_CLASSES`) reads the JWT from `request.COOKIES.get("access_token")` instead of the `Authorization` header, and enforces CSRF (mirroring DRF's `SessionAuthentication.enforce_csrf`) on every authenticated request — the browser sends the JWT cookie automatically, so all state-changing requests (checkout, order creation, admin writes, logout) require a valid `X-CSRFToken` header matching the `csrftoken` cookie
  - Cookies use `secure=not settings.DEBUG` and `samesite="Lax"`; `CORS_ALLOW_CREDENTIALS = True` and `CSRF_TRUSTED_ORIGINS` (env var, defaults to `http://localhost:5173`) are required for the cross-origin Vite frontend to send/receive them
- Default permission: `IsAuthenticated` (all endpoints require the cookie-based token)
- `produtos` ViewSets (Categoria, Marca, Produto, Variacao) use `IsAdminOrReadOnly` (`produtos/permissions.py`) — reads are public, writes require `request.user.is_staff`
- `PedidoViewSet` uses `IsAuthenticated` + `IsDonorOrStaff` (`pedidos/permissions.py`) and filters `get_queryset()` so non-staff users only see their own orders (staff see all); `perform_create()` auto-assigns `usuario` from `request.user`, so clients never submit it. `perform_create()` also rejects (403) a non-staff request that tries to link an `endereco` id belonging to a different user — same shape of check as `ItemPedidoViewSet` below, added alongside the `Pedido.endereco` FK precisely to avoid opening a new IDOR the moment the field became client-writable (a malicious `POST /pedidos/` could otherwise link someone else's saved address to your own order, leaking that it exists/its contents via `endereco_detalhe` on every future read of the order). `perform_create()` also accepts an optional `itens_criacao` list and, when present, creates the `Pedido` and every `ItemPedido` line together inside one `transaction.atomic()` block — see the fixed "order creation isn't atomic" quirk below for the full design
- `EnderecoViewSet` uses `IsAuthenticated` + `IsDonorOrStaff`, filters `get_queryset()` by `usuario=request.user` (staff see all), and `perform_create()` forces `usuario=request.user` — closes an IDOR that let any authenticated user read/edit/delete another user's address. `usuario` is also `read_only` on `EnderecoSerializer` (root-cause fix, see below), and `perform_update()` explicitly re-asserts `serializer.instance.usuario` on save — belt-and-suspenders against a `PUT`/`PATCH` payload trying to reassign an address to a different user's id; deliberately uses the *existing* owner rather than `self.request.user`, since a staff edit of someone else's address must not silently reassign it to the staff member. `perform_destroy()` catches `django.db.models.deletion.ProtectedError` (raised when the address is still linked to a `Pedido` via the `PROTECT` FK) and re-raises it as a DRF `ValidationError` (`{"detail": "Este endereço não pode ser excluído porque está vinculado a um ou mais pedidos."}`, 400) — see the fixed quirk below
- `ItemPedidoViewSet` uses `IsAuthenticated` + `IsItemDonorOrStaff` (`pedidos/permissions.py`), filters `get_queryset()` by `pedido__usuario=request.user` (staff see all); `perform_create()` raises `PermissionDenied` (403) if a non-staff user targets a `Pedido` they don't own, and always sets `preco_unitario` server-side from `variacao.produto.preco` — the field is `read_only` on `ItemPedidoSerializer`, so clients can't forge a price or attach items to someone else's order. `perform_create()` also raises a DRF `ValidationError` (`{"detail": "Estoque insuficiente. Restam apenas N unidades."}`, 400) if `quantidade` exceeds `variacao.estoque`, checked *before* `serializer.save()` — see the fixed quirk below for why the check lives here rather than only in the `diminui_estoque` signal
- `/api/registro/` uses `AllowAny`
- `usuarios/views.py::MeView` (`GET /api/me/`, `IsAuthenticated`) returns the current user via `MeSerializer` (id, username, email, is_staff) — used by the frontend to hydrate/validate the session on load and after login
- Token endpoints: `POST /api/token/` (obtain, throttled), `POST /api/token/refresh/` (refresh), `POST /api/logout/` (clears cookies, requires auth)

### Rate Limiting

- `DEFAULT_THROTTLE_CLASSES` = `ScopedRateThrottle`; only views with a `throttle_scope` attribute are throttled, so the rest of the API is unaffected
- `/api/token/` (`core/views.py::ThrottledTokenObtainPairView`, `throttle_scope = "login"`) and `/api/registro/` (`throttle_scope = "registro"`) are limited to 5 requests/min per client via `DEFAULT_THROTTLE_RATES` in `core/settings.py`

### Environment Variables

- `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, and `CORS_ALLOWED_ORIGINS` are loaded via `python-decouple` (`core/settings.py`) instead of being hardcoded
- Local values live in `backend/.env` (gitignored); `backend/.env.example` documents the expected variables
- `CORS_ALLOW_ALL_ORIGINS` is tied to `DEBUG` — all origins allowed only in dev; in production only origins listed in `CORS_ALLOWED_ORIGINS` are accepted

### Query Optimization

`ProdutoViewSet` uses `select_related("marca", "categoria").prefetch_related("variacoes")` to avoid N+1 queries, with a default `order_by("nome")` so pagination is always deterministic (avoids `UnorderedObjectListWarning`); clients can still override via the `ordering` query param (`ordering_fields`: nome, preco). Supports `filterset_fields`, `search_fields` (nome, marca__nome).

### Django Admin

`pedidos/admin.py` customizes the admin for order management:

- **PedidoAdmin** — `list_display` (id, usuario, status, total, data_pedido), `list_filter` (status, data_pedido), `search_fields` (usuario__username), with an `ItemPedidoInline` to view/edit order items directly on the order page
- **ItemPedidoAdmin** — `list_display` (pedido, variacao, quantidade, preco_unitario, subtotal), `list_filter` (pedido__status)
- **EnderecoAdmin** — `list_display` (usuario, rua, cidade, estado)

## DRF Configuration

- Pagination: `PageNumberPagination`, 10 items per page
- Filter backends: `DjangoFilterBackend`, `SearchFilter`, `OrderingFilter`
- Auth: `core.authentication.CookieJWTAuthentication` (JWT read from the `access_token` cookie, not the `Authorization` header; enforces CSRF on authenticated requests)
- Throttling: `ScopedRateThrottle`, applied only to `/api/token/` and `/api/registro/` (5/min each)
- CORS: all origins allowed only when `DEBUG=True`; restricted to `CORS_ALLOWED_ORIGINS` in production; `CORS_ALLOW_CREDENTIALS = True` so the frontend can send/receive the auth cookies cross-origin

## Frontend (`frontend/`)

React 19 + Vite + Tailwind + shadcn/ui, using `react-router-dom` for routing.

- **`src/lib/axios.js`** — shared Axios instance (`api`), `baseURL` from `VITE_API_URL` (defaults to `http://localhost:8000/api`), `withCredentials: true` so the httpOnly JWT/CSRF cookies flow cross-origin
  - Request interceptor attaches `X-CSRFToken` (read from the `csrftoken` cookie) on state-changing methods (`post`, `put`, `patch`, `delete`), matching the backend's CSRF enforcement
  - Response interceptor catches a `401`, calls `POST /token/refresh/` once (deduped via a module-level `isRefreshing`/`refreshPromise` pair so concurrent 401s share a single refresh call), then retries the original request; requests already flagged `_retry`, or the refresh call itself, are not retried again to avoid loops
- **`src/contexts/AuthContext.jsx`** — `AuthProvider` + `useAuth()` hook; on mount calls `GET /me/` to hydrate `user` (`isLoading` covers this initial check); exposes `login(username, password)` (`POST /token/`, then `GET /me/`), `register(dados)` (`POST /registro/`), and `logout()` (`POST /logout/`, always clears local `user`); `isAuthenticated` is derived as `!!user`; on failure, both `login` and `register` resolve `{ success: false, error }` where `error` is the raw DRF error payload (`{ detail }` or `{ campo: [...] }`), not a pre-extracted string — kept raw so callers can map it onto a form (see `src/lib/apiErrors.js`)
- **`src/contexts/CartContext.jsx`** — `CartProvider` + `useCart()` hook; cart state (`itens`) is frontend-only — loaded from and persisted to `localStorage` (key `"carrinho"`, via a `useEffect` on every change) — with no backend persistence until a `Pedido` is created at checkout; each item is keyed by `variacaoId` (a `Variacao` already belongs to exactly one `Produto`, so it's a sufficient unique key) and carries a snapshot of `estoque` taken when added; exposes `adicionarItem(produto, variacao, quantidade)` (merges into an existing line for the same `variacaoId` instead of duplicating), `removerItem(itemId)`, `atualizarQuantidade(itemId, novaQuantidade)` (clamped to `[1, estoque]` — dropping to 0 removes the line rather than leaving a zero-quantity row), `limparCarrinho()`, and derived `totalItens`/`totalValor`
- **`src/components/PrivateRoute.jsx`** — route guard using `useAuth()`; renders a loading state while `isLoading`, redirects to `/login` (via `Navigate replace`, passing `state={{ from: location }}`) when not authenticated, otherwise renders the nested route (`Outlet`)
- **`src/App.jsx`** — wraps the app in `AuthProvider` + `CartProvider` (independent of each other, order doesn't matter) + `BrowserRouter`, renders `Header` above `Routes`. Routes: `/` (`Catalogo`, product grid), `/produtos/:id` (`ProdutoDetalhe`), `/carrinho` (`Carrinho`, public — no `PrivateRoute`), `/login` and `/registro` (real forms, see below), and behind `PrivateRoute`: `/checkout` (`Checkout`), `/pedido-confirmado` (`PedidoConfirmado`, inline placeholder — shows `location.state.pedidoId` when present), `/meus-pedidos` (`MeusPedidos`, order history), `/meus-pedidos/:id` (`PedidoDetalhe`, single order view), and `/meus-enderecos` (`MeusEnderecos`, saved-address management)
- **`src/components/Header.jsx`** — minimal/temporary header (full styling later): shows the logged-in username + a "Sair" button (`logout()` then redirect home) when authenticated, or a "Login" link otherwise; also shows a cart icon linking to `/carrinho` with a badge (`useCart().totalItens`, hidden at 0), visible regardless of auth state; "Meus Pedidos" and "Meus Endereços" links are likewise always rendered (not conditioned on `isAuthenticated`) — both routes are behind `PrivateRoute`, which handles the redirect-to-login itself
- **Forms (`react-hook-form` + `zod`, via `@hookform/resolvers/zod`)** — the established pattern for all forms in this project (login/registro/endereço so far):
  - One schema file per form in `src/schemas/` (e.g. `loginSchema.js`, `registroSchema.js`, `enderecoSchema.js`); cross-field validation (e.g. password confirmation) uses Zod's `.refine()` with an explicit `path`
  - `src/lib/apiErrors.js::applyApiErrors(errorData, setError, setGeneralError)` — shared helper that maps a DRF error payload onto the form: `{ detail }` → general banner via `setGeneralError`, `{ campo: ["msg"] }` → per-field via react-hook-form's `setError`; reuse this for every new form instead of writing bespoke error-mapping
  - `src/pages/Login.jsx` and `src/pages/Registro.jsx` are the reference implementation of the pattern (schema + `useForm({ resolver: zodResolver(schema) })` + `applyApiErrors` on failure). `src/pages/Checkout.jsx` is a variant: the address form is only one part of a bigger page action, so it drives `useForm` manually (`trigger()` + `getValues()` + `enderecoSchema.parse()`) from a plain button handler instead of wrapping everything in `handleSubmit()` — needed because `handleSubmit` would validate the address schema even when the user picked an existing saved address and left the fields empty
- **`src/components/ui/input.jsx`, `src/components/ui/label.jsx`** — plain shadcn-style form primitives (native `<input>`/`<label>`, not base-ui primitives) added alongside the existing `button.jsx`
- **`src/api/`** — one function-per-resource module per REST resource, using the shared `api` axios instance; `produtos.js` is the first one: `listarProdutos({ categoria, marca, search, ordering, page })`, `buscarProduto(id)`, `listarCategorias()`, `listarMarcas()` — the last two follow the API's `next` link to the end since `/categorias/` and `/marcas/` are paginated too (10/page) and the catalog currently has more than 10 of each
  - `enderecos.js` — `listarEnderecos()` (same follow-`next`-to-the-end pagination pattern, in case a user ever has 10+ saved addresses), `criarEndereco(dados)`, `atualizarEndereco(id, dados)` (`PATCH /enderecos/{id}/` — partial update, since the "edit" UI only ever changes address fields, never `usuario`; note `usuario` is `read_only` on the serializer now, so a `PUT` would work fine too, this is just a UX/payload-shape choice, not a workaround), `deletarEndereco(id)` (`DELETE /enderecos/{id}/`)
  - `pedidos.js` — `criarPedido({ endereco, itens })` (`POST /pedidos/`; both params optional and each omitted entirely — not sent as `null`/`[]` — when not passed, since the underlying model/serializer fields are optional; `usuario` is auto-assigned server-side, `status`/`total` have defaults). `itens`, when passed, is mapped to the `itens_criacao` payload field (`[{variacao, quantidade}]`) so the Pedido and every line are created together in one atomic backend call — see `PedidoViewSet.perform_create()` and the fixed "order creation isn't atomic" quirk below; `criarPedido({ endereco })` alone (no `itens`) still creates an empty Pedido exactly like before. `criarItemPedido({ pedido, variacao, quantidade })` (`POST /itens/`, adds a single line to an existing Pedido) and `deletarPedido(id)` (`DELETE /pedidos/{id}/`) are both unused by the UI now that `criarPedido()` handles the whole checkout in one call, but kept as direct bindings since both endpoints are still live and supported — see the fixed quirk below for why. `listarPedidos({ page })` (`GET /pedidos/`) uses real pagination — passes `page` straight through and returns the raw `{count, next, previous, results}` payload, unlike `listarCategorias()`/`listarMarcas()` which follow `next` to the end; order history is unbounded per user, so page-by-page controls (same UX as `listarProdutos()`) make more sense than loading everything upfront. `buscarPedido(id)` (`GET /pedidos/{id}/`). Both rely on `PedidoViewSet.get_queryset()` already filtering to the current user's own orders (staff see all), so requesting another user's order `id` returns a 404, not a 403
- **`src/pages/Catalogo.jsx`** (route `/`) — product grid consuming `/api/produtos/`; search (debounced 400ms), categoria/marca filters, price ordering, and pagination (via `count`/`next`/`previous`) are all synced to the URL through `useSearchParams`, so filtered views are shareable links and work with browser back/forward
- **`src/pages/ProdutoDetalhe.jsx`** (route `/produtos/:id`) — single product view (marca, nome, categoria, preço, variações); out-of-stock sizes are shown alongside in-stock ones with a disabled/"Esgotado" treatment rather than being omitted; in-stock sizes are clickable buttons (`aria-pressed`), selecting one reveals a quantity stepper (`+`/`-`, clamped to `[1, estoque]`) and enables "Adicionar ao carrinho" (`useCart().adicionarItem`), which shows "Adicionado!" for 1.5s as feedback
- **`src/pages/Carrinho.jsx`** (route `/carrinho`, public) — lists cart lines (`useCart().itens`) with placeholder image, product name (linking back to `/produtos/:id`), tamanho, unit price, a quantity stepper wired to `atualizarQuantidade` (the `+` button disables at `estoque`), per-line subtotal, and a remove button (`removerItem`); shows an empty-state message + link to the catalog when `itens` is empty — that message is either the default or `location.state.mensagem`, so a redirect (e.g. from `Checkout.jsx` when the cart is empty) can explain why the user landed here; ends with the running total and a "Finalizar compra" button linking to `/checkout`
- **`src/pages/Checkout.jsx`** (route `/checkout`, behind `PrivateRoute`) — redirects to `/carrinho` (with an explanatory `state.mensagem`) if the cart is empty. Address step: fetches the user's saved `Endereco`s (`listarEnderecos()`) and shows them as a radio list (first one pre-selected) plus a "Cadastrar novo endereço" option; picking that (or having zero saved addresses) reveals the `enderecoSchema`-validated form. Order summary: read-only list of cart lines (no editing here — that's what `/carrinho` is for), a fixed `FRETE_PLACEHOLDER` (R$20, labeled as temporary — **no real SuperFrete calculation yet, tracked separately**), and the total. "Confirmar pedido": if a new address was filled in, POSTs it first (`criarEndereco`, errors mapped onto the form via `applyApiErrors`) and captures the returned `id`; otherwise uses the id of the selected saved address. Either way, that `enderecoId` and the cart lines are passed together to a single `criarPedido({ endereco: enderecoId, itens })` call, so every new order is created atomically with its items and linked to the address it was actually placed against (see the `Pedido.endereco` FK below and the fixed "order creation isn't atomic" quirk further down) — no partial-order rollback logic needed on this page anymore. On success, `limparCarrinho()` and navigate to `/pedido-confirmado` with `state.pedidoId`; on failure, a general error banner prefers the backend's `detail` message (e.g. an insufficient-stock message naming the specific line) over a generic fallback — the cart is left untouched so the user can retry
- **`PedidoConfirmado`** — a small inline placeholder component in `App.jsx`, shown after a successful checkout; will grow into a real order confirmation view during the "Área do Cliente" phase
- **`src/pages/MeusPedidos.jsx`** (route `/meus-pedidos`, behind `PrivateRoute`) — order history list consuming `listarPedidos()`; each row (linking to `/meus-pedidos/:id`) shows order number, date, a `PedidoStatusBadge`, and total; real pagination controls (same Anterior/Próxima pattern as `Catalogo.jsx`, synced to the URL via `useSearchParams`); handles loading, a fetch-error message, and an empty state ("Você ainda não fez nenhum pedido" + link to the catalog). Uses the same `{ chave, ... }`-keyed result state as `Catalogo.jsx` (comparing a stringified `{ page }` key against the last-loaded one) instead of a separate `isLoading` flag set inside the effect, to satisfy the `react-hooks/set-state-in-effect` lint rule
- **`src/pages/PedidoDetalhe.jsx`** (route `/meus-pedidos/:id`, behind `PrivateRoute`) — single order view consuming `buscarPedido(id)`; shows order number, date, `PedidoStatusBadge`, the nested `itens` (`produto_nome`, `produto_tamanho`, `quantidade`, `preco_unitario`, `subtotal`), and the order total. Also shows a "Endereço de entrega" section (same "rua, número - complemento — bairro, cidade/UF — CEP" format as `Checkout.jsx`/`MeusEnderecos.jsx`) when `pedido.endereco_detalhe` is present — orders placed before the `Pedido.endereco` FK existed simply omit the section rather than showing an empty/broken one. A 404 (order doesn't exist, or belongs to another user — `PedidoViewSet.get_queryset()` already filters by owner, so this is indistinguishable from "doesn't exist" and is treated as such) renders a friendly "Pedido não encontrado." message with a link back to `/meus-pedidos` instead of an unhandled error; other failures fall back to a generic error message. Same key-based loading pattern as `MeusPedidos.jsx`
- **`src/components/PedidoStatusBadge.jsx`** — small colored pill mapping each `Pedido.status` choice (`novo`/`confirmado`/`enviado`/`entregue`/`cancelado`) to a label and a Tailwind color class; shared by `MeusPedidos.jsx` and `PedidoDetalhe.jsx`
- **`src/pages/MeusEnderecos.jsx`** (route `/meus-enderecos`, behind `PrivateRoute`) — lists the user's saved `Endereco`s (`listarEnderecos()`) in the same "rua, número - complemento — bairro, cidade/UF — CEP" format used in `Checkout.jsx`; each row has "Editar" and "Excluir" buttons. Editing is inline: clicking "Editar" swaps that row's display for an `EnderecoForm` (see below) prefilled via `atualizarEndereco(id, dados)`; only one row (or the "new address" form) can be in edit mode at a time, tracked by a single `modoEdicao` state (`null` / an `Endereco.id` / the `"novo"` sentinel) rather than per-row state — simplest option that still supports the one-at-a-time editing flow. "Adicionar novo endereço" reveals the same `EnderecoForm` in create mode (`criarEndereco()`, still needs the `usuario: user.id` workaround described above since creation goes through `perform_create()`, not `PATCH`). "Excluir" confirms via a plain `window.confirm()` (no custom modal for this pass) before calling `deletarEndereco(id)`; the delete-error banner prefers `error.response?.data?.detail` (e.g. the "vinculado a um ou mais pedidos" message below) over its generic fallback, same pattern as `Checkout.jsx`. Handles loading, a fetch-error message, a separate delete-error banner, and an empty state ("Nenhum endereço cadastrado ainda")

Backend quirks discovered while building the checkout flow (frontend works around them; not fixed at the source since that's out of this phase's scope):
- **Fixed 2026-07-24 — was a real IDOR, not just a quirk:** `EnderecoViewSet` didn't override `perform_update()` (only `perform_create()`), and `EnderecoSerializer` had `usuario` as a plain writable field. Since `IsDonorOrStaff`'s object-level check only confirms the caller owns (or is staff for) the address being edited — it says nothing about what *values* can be written — any authenticated user could `PUT`/`PATCH` `/api/enderecos/{id}/` on their own address with `usuario: <outro_id>` in the body and reassign that address to another user's account. This only affected direct API use (curl/Postman/etc) — the frontend never sent `usuario` on edit (see below), so the UI itself couldn't trigger it. **Fix:** `usuario` is now `read_only` on `EnderecoSerializer` (`pedidos/serializers.py`) — the root-cause fix, chosen over a model-level `blank=True`/`null=True` change because (a) it needs no migration, (b) it's semantically correct (an `Endereco` should never actually have a null owner — the model constraint should stay required), and (c) `blank=True`/`null=True` alone wouldn't have closed the vulnerability anyway, since it only affects requiredness/nullability, not writability — a still-writable field remains just as attackable. `EnderecoViewSet.perform_update()` (`pedidos/views.py`) was also added, re-asserting `serializer.instance.usuario` on every save as defense in depth (technically redundant once the field is read-only, since DRF excludes read-only fields from `validated_data` entirely, but cheap insurance if the serializer ever changes). Manually verified via curl: authenticated as user A, a `PUT` (all required fields + `usuario: <user B's id>`) and a `PATCH` (`{"usuario": <user B's id>}`) against user A's own address both returned `200` with the edit applied, but `usuario` stayed A's id in both cases.
- `Endereco.usuario` still has no `blank=True`/`null=True` on the model (deliberately — see above), so `EnderecoSerializer` requires *some* value be resolvable, but since the field is now `read_only`, the client no longer needs to (and can't usefully) supply it at all — `perform_create()` still supplies it explicitly via `serializer.save(usuario=self.request.user)`, same as before. This makes the frontend's `usuario: user.id` payload field vestigial: `src/pages/Checkout.jsx` (the `criarEndereco({ ...enderecoSchema.parse(getValues()), usuario: user.id })` call) and `src/pages/MeusEnderecos.jsx` (`handleCriar`'s `{ ...dados, usuario: user.id }`) both still send it, but the backend now silently ignores it either way — harmless, but worth deleting next time either file is touched, since it no longer does anything.
- **Fixed 2026-07-25:** `Pedido` previously had no FK to `Endereco` at all, so the address collected/created at checkout was saved to the user's account (reusable later) but wasn't linked to the specific order it was entered for. **Fix:** added `Pedido.endereco` (`pedidos/models.py`, migration `0008_pedido_endereco`) — `ForeignKey("Endereco", on_delete=models.PROTECT, null=True, blank=True, related_name="pedidos")`. `PROTECT` (not `SET_NULL`/`CASCADE`) because a historical order's shipping address must never silently disappear or drag the whole order down with it — same reasoning already used for `ItemPedido.variacao`. `null=True, blank=True` because it's a new field on an existing table — pre-existing `Pedido` rows have no address to backfill, and making it required would need a data migration with no real address to put there. Note this is a live FK, not a snapshot: if a user later edits the linked `Endereco` via `MeusEnderecos.jsx`, the order's displayed address changes too, since `endereco_detalhe` always reflects the current row — full point-in-time immutability would need copying the address fields onto `Pedido` at order time instead of referencing them, which is out of scope for this fix. `PedidoSerializer` now exposes both `endereco` (writable id, via `criarPedido({ endereco })`) and `endereco_detalhe` (nested, read-only, `source="endereco"`) — mirroring how `itens` is nested-read/separately-written. `PedidoViewSet.perform_create()` was extended to 403 a non-staff request whose `endereco` belongs to a different user (see above) — this check didn't exist before because the field didn't exist; it closes the same class of IDOR fixed on `EnderecoViewSet` itself, at the point the FK was introduced, rather than shipping it and fixing it later.
- **Fixed 2026-07-27 — quirk introduced by the `Pedido.endereco` fix above:** `EnderecoViewSet` didn't catch `ProtectedError`, so `DELETE /enderecos/{id}/` on an address linked to any `Pedido` (via the `PROTECT` FK) raised an unhandled 500 instead of a clean 400. **Fix:** `EnderecoViewSet.perform_destroy()` (`pedidos/views.py`) now wraps `instance.delete()` in `try`/`except ProtectedError`, re-raising as `rest_framework.exceptions.ValidationError({"detail": "Este endereço não pode ser excluído porque está vinculado a um ou mais pedidos."})` — same `{"detail": ...}` shape as the `diminui_estoque` fix above, and the same reasoning for why (DRF's `exception_handler` only produces that shape for a dict-wrapped `detail`; a bare string gets coerced into a raw JSON list instead). No propagation surprises here: `ProtectedError` is raised directly by `instance.delete()` inside `perform_destroy()`, itself called synchronously from `DestroyModelMixin.destroy()` within the view's own call stack — not from a signal — so there was never a question of whether the exception would reach DRF's handler. Verified via curl: created an `Endereco` linked to a `Pedido` and one unlinked; `DELETE` on the linked one now returns a clean `400` with the message above and the address row remains in the database (confirmed via shell), while `DELETE` on the unlinked one still returns `204` and actually removes the row. `MeusEnderecos.jsx`'s delete-error handler was updated to prefer `error.response?.data?.detail` over its generic fallback (same pattern as `Checkout.jsx`), so the precise message now reaches the user instead of the generic "Tente novamente."
- **Fixed 2026-07-26:** `diminui_estoque` (`pedidos/signals.py`) used to raise a bare `ValueError` on insufficient stock, so `POST /itens/` returned an unhandled 500 (HTML error page) instead of a clean 400. **Fix:** it now raises DRF's `rest_framework.exceptions.ValidationError({"detail": "Estoque insuficiente. Restam apenas N unidades."})` — the `detail` is wrapped in a dict rather than passed as a bare string, because `ValidationError.__init__` coerces any non-dict/non-list detail into a bare list (`["msg"]`), which DRF's exception handler then returns as a raw JSON array instead of `{"detail": "msg"}"`; wrapping it keeps the shape consistent with every other error in this API (e.g. `PermissionDenied` usages in `views.py`), which is what the frontend already expects. Verified via curl (login, create a `Pedido`, `POST /itens/` with `quantidade` > `estoque`) that this reaches the client as a real `400` with `{"detail": "Estoque insuficiente. Restam apenas 3 unidades."}` — signals are sent synchronously (`Signal.send`, not `send_robust`) from within `instance.save()`, which itself runs inside the view's call stack, so an exception raised in a `post_save` receiver propagates through DRF's `dispatch()` exception handling exactly like one raised directly in a view. **However, propagating the right status code wasn't the whole story:** since `ATOMIC_REQUESTS` isn't enabled (see `core/settings.py::DATABASES`), `ItemPedido.save()` commits its `INSERT` immediately, *before* the `post_save` signal (and its own separate `@transaction.atomic` block) even runs — so raising from inside the signal returned a correct `400` while silently leaving an invalid `ItemPedido` row committed in the database (confirmed via the same curl reproduction: the over-quantity row existed in `pedido.itens` afterwards, just never reflected in `Pedido.total` since the exception also stops the later `atualiza_total_pedido` receiver from running — `Signal.send` stops calling remaining receivers once one raises). **Root-cause fix:** the authoritative stock check now lives in `ItemPedidoViewSet.perform_create()` (`pedidos/views.py`), raising the same `ValidationError` *before* `serializer.save()` is ever called, so the invalid row is never created at all. `diminui_estoque`'s own check stays in place as a defense-in-depth backstop for creation paths that don't go through this view (e.g. the Django admin's `ItemPedidoInline`) — though note a `rest_framework.exceptions.ValidationError` raised there isn't caught by Django admin's form handling either (it's not `django.core.exceptions.ValidationError`), so an admin-side insufficient-stock save would still surface as an unhandled 500; that's a pre-existing gap (the original `ValueError` had the same problem there) and out of scope for this fix. Re-verified via curl after the `perform_create()` change: the same over-quantity request still returns `400` with the same message, and this time no `ItemPedido` row is created and `Variacao.estoque` is left untouched; a valid follow-up request (`quantidade` within stock) still creates the item, decrements `estoque`, and updates `Pedido.total` correctly. On the frontend, `Checkout.jsx`'s error handling (`error.response?.data?.detail || <generic fallback>`) needed no change — it already preferred `detail` when present, it just never had one to use while the backend returned an HTML 500 body; now that `detail` is populated, the precise message surfaces automatically.
- **Fixed 2026-07-27:** Order creation used to not be atomic — there was no backend endpoint that created a `Pedido` and its `ItemPedido` lines in one transaction, so `Checkout.jsx` created the Pedido first, then looped `criarItemPedido()` per cart line. If an item failed partway (e.g. insufficient stock on one line), the Pedido was left orphaned with only a partial set of items; the frontend mitigated this by calling `deletarPedido(pedido.id)` on a mid-loop failure, swallowing any failure of that cleanup call itself (best-effort, not blocking) — a workaround, not a fix for the underlying partial-failure window. **Fix:** `PedidoSerializer` (`pedidos/serializers.py`) gained a write-only `itens_criacao` field — `ItemPedidoCriacaoSerializer(many=True, write_only=True, required=False)`, each entry `{variacao, quantidade}` — kept as a separate field rather than making the existing `itens` field writable, since `itens` is `ItemPedidoSerializer` built for *reading* an already-persisted line (exposes `id`, `produto_nome`, `subtotal`, etc., none of which make sense on input) and requires a `pedido` that doesn't exist yet at creation time. `PedidoViewSet.perform_create()` (`pedidos/views.py`) pops `itens_criacao` out of `validated_data` (it isn't a real `Pedido` field, so `ModelSerializer`'s default `.create()` would otherwise pass it straight to `Pedido.objects.create(**validated_data)` and raise an unexpected-keyword-argument error) and, inside a single `with transaction.atomic():` block, saves the `Pedido` and then loops the items, creating each `ItemPedido` via `.objects.create()` — which still fires the existing `calcula_subtotal`/`diminui_estoque`/`atualiza_total_pedido` signals unchanged, so subtotal calculation, stock decrementing, and running-total maintenance are all reused as-is, not reimplemented. Before creating each line, the loop re-fetches the `Variacao` fresh from the DB (`Variacao.objects.get(pk=...)`, not the `PrimaryKeyRelatedField` instance cached in `validated_data` from up-front payload validation) and checks `estoque >= quantidade`, raising the same `{"detail": ...}`-shaped `ValidationError` used elsewhere in this API if not — same authoritative-check-before-create pattern as `ItemPedidoViewSet.perform_create()`, needed here so a repeated `variacao` id within the same batch sees the previous line's decrement rather than the pre-request stock level (the outer `transaction.atomic()` would also roll back correctly if the `diminui_estoque` signal's own check fired instead, since everything in the block — Pedido, prior `ItemPedido`s, prior stock decrements — is part of the same uncommitted transaction, but checking explicitly first keeps both creation paths consistent and names the specific failing item in a batch). **Same endpoint, not a new route:** `POST /pedidos/` now accepts an optional `itens_criacao` list rather than gaining a separate creation endpoint — creating an order together with its lines is still creating one `Pedido` resource, a new route would duplicate the ownership/`endereco` checks already in `perform_create()`, and the old call shape (`POST /pedidos/` with no body, then `POST /itens/` per line) keeps working completely unchanged, since an omitted `itens_criacao` just means the loop never runs. Verified via curl: a 2-item request where the second line's `quantidade` exceeds its `estoque` returns a clean `400` naming that line, and neither the `Pedido` nor the first (individually valid) `ItemPedido` end up in the database, nor is any stock decremented — confirmed by querying the DB directly after the call. A subsequent all-valid 2-item request returns `201` with both lines and the correct summed `total`, and each `Variacao.estoque` is decremented correctly. The pre-existing empty-`POST /pedidos/`-then-`POST /itens/` flow and the address-ownership 403 check were both re-verified working unchanged. On the frontend, `Checkout.jsx` now makes one `criarPedido({ endereco, itens })` call instead of `criarPedido()` + a `criarItemPedido()` loop, and no longer calls `deletarPedido()` on failure — there's no orphaned Pedido to clean up anymore. `criarItemPedido()` and `deletarPedido()` (`pedidos.js`) are now unused by the UI but were kept as direct bindings rather than deleted, since `POST /itens/` and `DELETE /pedidos/{id}/` are still live, supported endpoints — `criarItemPedido()` for a possible future "add a line to an existing order" feature, `deletarPedido()` for a possible future "cancelar pedido" feature.
- **Known limitation, not fixed here — stock decrement isn't safe against concurrent requests for the same `Variacao`:** `diminui_estoque` (`pedidos/signals.py`) checks `variacao.estoque < instance.quantidade` and then does `variacao.estoque -= instance.quantidade; variacao.save()` — a plain Python read-modify-write to an absolute value, not an atomic SQL update (e.g. `Variacao.objects.filter(pk=variacao.pk, estoque__gte=quantidade).update(estoque=F("estoque") - quantidade)`), and none of the three places that read a `Variacao` for a stock check (`ItemPedidoViewSet.perform_create()`, the `itens_criacao` loop in `PedidoViewSet.perform_create()` above, and `diminui_estoque` itself) use `select_for_update()` to lock the row. Two different clients (separate DB connections) racing for the last unit(s) of the same `Variacao` can both read the same pre-decrement `estoque`, both pass the check, and both write an absolute new value — a lost update: the second write silently overwrites the first's decrement instead of compounding it, so stock ends up overcounted (both requests "succeed") instead of the second being correctly rejected. This predates every stock-related fix in this document and none of them touch it: the `ValidationError` fix made a *failed* check return a clean `400` instead of `500`, the `ItemPedidoViewSet.perform_create()` fix stopped an *invalid* item from being persisted despite that clean `400`, and the `itens_criacao` re-fetch above only guards one order's *own* multiple lines for the same `Variacao` against each other within a single transaction — none of the three add row locking across requests. It's substantially masked in the current dev setup because SQLite serializes writers at the whole-database level (a second write transaction blocks until the first commits or rolls back, incidentally preventing the interleaving needed to trigger the lost update) — an accidental side effect of SQLite's locking model, not a guarantee from the application code. Under PostgreSQL (`READ COMMITTED` by default, row-level MVCC, no whole-database write lock — the Phase 5 target), the race is real. Worth fixing before or during that migration, most simply via `select_for_update()` on the `Variacao` fetch at each of the three call sites above, or by switching the decrement itself to the atomic `.update(estoque=F(...) - quantidade)` form and checking the returned row count instead of a separate read-then-check.
