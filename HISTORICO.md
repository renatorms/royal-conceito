## Django Admin — histórico de bloqueio de campos calculados/derivados

Movido de baixo do cabeçalho "### Django Admin" do CLAUDE.md — a entrada original começava logo após a descrição de `PedidoAdmin`/`ItemPedidoAdmin`/`EnderecoAdmin` (que continuam no CLAUDE.md, por descreverem a configuração atual do admin, não uma correção já finalizada). Este bloco narra, em ordem cronológica, seis incidentes distintos entre 27/07 e 01/08 (`preco_unitario`/`subtotal` editáveis, `pedido`/`variacao` reatribuíveis em `ItemPedido`, `usuario`/`endereco` reatribuíveis em `Pedido` — inclusive uma vulnerabilidade real na própria API, não só no admin —, `produto_nome`/`produto_tamanho` derivados ao vivo em vez de congelados, os campos de frete com a mesma lacuna, e um 500 real por `IntegrityError` no `VariacaoInline`).

- **Fixed 2026-07-27 — `preco_unitario`/`subtotal` were editable in the admin, despite being server-computed everywhere else:** both fields are always set by the backend — `preco_unitario` from `variacao.produto.preco` in `ItemPedidoViewSet.perform_create()`, `subtotal` by the `calcula_subtotal` signal — and both are `read_only` on `ItemPedidoSerializer`, so the API never lets a client set them. But neither `ItemPedidoAdmin` nor `ItemPedidoInline` (on `PedidoAdmin`) had any `readonly_fields`, so a staff member could freely retype either value in the admin, drifting an order's recorded price away from the real product price with no trace of it happening. **Fix:** both (`pedidos/admin.py`) now override `get_readonly_fields()` to mark `preco_unitario`/`subtotal` readonly *only when editing an existing `ItemPedido`* (`obj is not None`) — kept conditional rather than a plain `readonly_fields` list because `preco_unitario` has no model default and isn't nullable; making it readonly unconditionally would also remove it from the *add* form, and saving a brand-new row with no value for a `NOT NULL` column raises a DB integrity error. Confirmed via curl (admin session login, not the JWT API) that: the existing-item change page renders both as plain `<div class="readonly">`/`<p>` text, not `<input>` elements, on both `ItemPedidoAdmin`'s own change page and the `Pedido` change page's inline; a `POST` to the change page with a forged `preco_unitario`/`subtotal` in the payload is silently ignored (values unchanged after save — Django excludes readonly fields from the `ModelForm` entirely, not just from rendering, so this isn't just a UI treatment); the standalone add page still renders both as editable `NumberInput`s (`step="0.01"`), confirmed by asking the user first — their team uses the admin only to review orders that already came through checkout, not to build orders from scratch there, so losing the ability to add a *new* `ItemPedido` with a manually-typed price via the admin (see the inline caveat below) was an acceptable trade-off, and keeping the add form usable outweighed forcing that path through readonly too. **Inline-specific caveat, also confirmed via curl:** `InlineModelAdmin.get_readonly_fields(request, obj=None)` receives the *parent* `Pedido` as `obj`, not the individual `ItemPedido` row — Django applies one `readonly_fields` list to the whole formset, not per row. Since a `Pedido` shown in this admin always already exists, this reliably makes both fields readonly for every existing line, but it also makes them readonly for any *new* row added via "Add another" on an existing `Pedido`'s page (its blank `preco_unitario` renders as `<p>-</p>`, not an input) — so adding a line to an existing order via the inline no longer works either, same underlying trade-off, accepted for the same reason. This made the originally-requested separate fix — swapping the default `NumberInput` for a plain `forms.TextInput` to hide the browser's spinner arrows — unnecessary: Django never renders a widget for a `readonly_fields` entry (it's excluded from `form.fields` and rendered as plain text via `AdminReadonlyField`), so there's no `<input>` left for a spinner to appear on in the change view; a widget override would have been dead code for these two fields. **The same problem existed on `Pedido.total`** — always set by the `atualiza_total_pedido` signal (the sum of `ItemPedido.subtotal`), `read_only` on `PedidoSerializer`, but freely editable in `PedidoAdmin` with no `readonly_fields` at all. **Fix:** `PedidoAdmin` (`pedidos/admin.py`) now has a plain `readonly_fields = ["total"]` — unconditional, unlike `ItemPedidoAdmin`/`ItemPedidoInline` above, because `Pedido.total` has `default=0` (`pedidos/models.py`), so excluding it from the add form can't hit a `NOT NULL` failure: a brand-new `Pedido` genuinely has no items yet, so `0` is the correct value there too, not just a safe fallback — no `get_readonly_fields(obj=None)` conditional needed. Confirmed via curl: the change page for an existing `Pedido` renders `total` as `<div class="readonly">250,00</div>`, no `<input name="total">` anywhere; the add page likewise has no `<input name="total">`; a `POST` to the change endpoint with `total=99999.99` left the stored value at `250.00` unchanged (`status`, an actually-editable field in the same request, updated normally, confirming the rest of the form still works); a `POST` to the add endpoint with `total=12345.00` created the `Pedido` successfully (no integrity error) with `total` at `0.00`, not the forged value. **Same pattern, different root cause — `ItemPedido.quantidade` was also freely editable in the admin:** unlike `preco_unitario`/`subtotal`/`total`, `quantidade` isn't server-computed — a customer picks it at checkout, and it's ordinary (non-`read_only`) input on `ItemPedidoSerializer` and the `itens_criacao` entries on `PedidoSerializer`. The bug here is narrower: `diminui_estoque` (`pedidos/signals.py`) only validates/decrements stock `if created:` (see "Business Logic via Signals" above) — editing `quantidade` on an *already-existing* `ItemPedido` changes it with no stock check and no corresponding `Variacao.estoque` adjustment at all, while `calcula_subtotal`/`atualiza_total_pedido` *do* rerun on every save, so `subtotal`/`total` silently recompute to match the new `quantidade` even though stock was never touched — a staff member could bump `quantidade` from 1 to 33 with zero validation and zero trace that stock wasn't checked, creating a real mismatch between what the system records as sold and what's physically in stock. **Fix:** same shape as the fields above — `get_readonly_fields()` on both `ItemPedidoAdmin` and `ItemPedidoInline` now also readonly `quantidade` when `obj is not None`, same conditional (no default, not nullable, so an unconditional readonly would break creating a new item), confirmed with the user this isn't a workflow they rely on — any real quantity adjustment should go through the API/checkout, which validates stock correctly. Confirmed via curl: the existing-item change page and the `Pedido` page's inline both render `quantidade` as plain readonly text (`<div class="readonly">2</div>` / `<p>2</p>`), the add page still has an editable `<input name="quantidade">`, and a `POST` to the change endpoint forging `quantidade=33` (alongside forged `preco_unitario`/`subtotal`) left all three values unchanged and caused no additional `Variacao.estoque` decrement. **Fixed 2026-07-27 (applied later the same day) — `ItemPedido.pedido`/`variacao` had the same gap, flagged by the audit above but not fixed at the time:** the `quantidade` fix's own audit (see the CLAUDE.md entry above it) had already found that reassigning `variacao` or `pedido` on an *existing* `ItemPedido` broke data integrity in two distinct ways, left unfixed pending the user's decision: (1) `diminui_estoque` only runs `if created:`, so reassigning `variacao` triggers no stock check/adjustment at all — neither is the old variação's stock restored, nor is the new one validated or decremented; (2) `atualiza_total_pedido` only recalculates `instance.pedido` (the order the item belongs to *after* the save) — reassigning `pedido` moves the line to a different order but leaves the *old* order's `total` stale, still counting a line that isn't its own anymore. **Fix:** same shape again — `get_readonly_fields()` on `ItemPedidoAdmin` and `ItemPedidoInline` now also readonly both FKs when `obj is not None` (neither has a default, both are required, so unconditional would break creating a new item); any real reassignment should go through the API instead (cancel/recreate the item), which validates stock and keeps both orders' totals correct. Confirmed via curl: the existing-item change page (`ItemPedidoAdmin`) renders both as readonly links (e.g. `<div class="readonly"><a href="/admin/produtos/variacao/80/change/">Produto - P</a></div>`); the add page still has editable `<select>`s for both; a `POST` to the change endpoint forging both `pedido` and `variacao` to different ids left both unchanged. One nuance found while testing the `Pedido` page's inline specifically: `pedido` was *already* rendered as a hidden field there before this fix (`<input type="hidden" name="itens-0-pedido" value="...">`), not an editable dropdown — Django's `InlineModelAdmin` auto-excludes the FK-to-parent from the visible inline form regardless of `readonly_fields`, tying every row to the parent's own id structurally. So adding `pedido` to the inline's readonly set is a no-op there specifically (harmless, kept for consistency with `ItemPedidoAdmin`) — the real gap it closes is on the *standalone* `ItemPedidoAdmin` change page (`/admin/pedidos/itempedido/{id}/change/`), where `pedido` was a genuinely editable dropdown before this fix, confirmed via the same forged-`POST` test above. `variacao`, unlike `pedido`, was a real editable field in both places and needed the fix in both; confirmed via a second forged `POST` sent through the inline's own formset (targeting `itens-0-variacao` on the `Pedido` change page) that it's rejected there too, not just on the standalone page. **Fixed 2026-07-27 (cosmetic follow-up, isolated from the data-integrity fixes above) — `preco_unitario`/`subtotal` still showed the browser's native spinner arrows on the *add* form:** the readonly fixes above only apply `obj is not None` — the *add* form (a genuinely new `ItemPedido`) still renders these as the `DecimalField` default `NumberInput`, spinner arrows and all, which look bad on currency values. **Fix:** a new `ItemPedidoForm(forms.ModelForm)` (`pedidos/admin.py`) sets `Meta.widgets = {"preco_unitario": forms.TextInput(), "subtotal": forms.TextInput()}`, wired in via `form = ItemPedidoForm` on both `ItemPedidoAdmin` and `ItemPedidoInline` — purely a rendering change, `Decimal` validation still comes from the model field itself. Has no effect once a field is actually readonly (readonly fields are excluded from `form.fields` entirely, so no widget from this `Meta` is ever used for them), so this doesn't interact with or weaken the data-integrity fixes at all — the two are fully independent of each other. `quantidade` was deliberately left alone — the user asked only for `preco_unitario`/`subtotal` (and `total`, see below), not the integer quantity stepper, which is arguably still useful UX. Confirmed via curl: the standalone `ItemPedidoAdmin` add page now renders `<input type="text" name="preco_unitario">`/`<input type="text" name="subtotal">` (previously `type="number"`), while `quantidade` in the same form is untouched (`type="number"`). `Pedido.total` doesn't need this treatment at all: it's in `PedidoAdmin`'s *unconditional* `readonly_fields` (see above — it has `default=0`, so it's excluded from the form on both add and edit), so there's no screen where it ever renders as an editable `NumberInput` to begin with. The `ItemPedidoInline`'s copy of this fix currently has no observable effect either, for a different reason: by this point every `ItemPedido` field (`pedido`, `variacao`, `quantidade`, `preco_unitario`, `subtotal`) is readonly whenever the parent `Pedido` already exists (which, per the admin's actual use, is always) — confirmed via curl that the inline's `__prefix__` empty-form template (what the "Add another" button clones) contains no visible input fields at all anymore, only the hidden `id`/`pedido` bookkeeping fields and the delete checkbox. The widget is still wired up on `ItemPedidoInline` for consistency with `ItemPedidoAdmin` and in case any of the other readonly conditions are ever relaxed, but there's currently no page where it changes what's rendered. **Fixed 2026-07-27 — `Pedido.usuario`/`endereco` had the exact same admin gap as `Endereco.usuario`, and this time the API itself was vulnerable too, not just the admin:** `PedidoAdmin` had no `readonly_fields` covering either field, so a staff member could reassign an existing `Pedido` — and its whole item history — to a different user, or link it to another user's saved address, directly through the change form; same class of bug as `Endereco.usuario` (24/07, then again in the admin 27/07). Unlike that fix, though, checking the API first (`PedidoViewSet`, `pedidos/views.py`) found it wasn't just the admin this time: `PedidoViewSet` had no `perform_update()` at all, and `usuario` was a normal writable field on `PedidoSerializer` (only `total` was in `read_only_fields`) — since `IsDonorOrStaff.has_object_permission()` only checks that the caller owns the *current* Pedido, never what values a request can write, a `PATCH`/`PUT /api/pedidos/{id}/` with `{"usuario": <other id>}` from the Pedido's real owner would have silently reassigned it, a genuine, un-mitigated IDOR — confirmed by reading the permission class (`pedidos/permissions.py::IsDonorOrStaff`) alongside the missing `perform_update()`, not just suspected. Separately, `endereco` is legitimately writable (that's how checkout links an order to an address), but its ownership check (`endereco.usuario == pedido owner`, unless staff) only ever lived in `perform_create()` — with no `perform_update()`, a `PATCH` could link an existing Pedido to another user's address with zero validation, the same leak-via-`endereco_detalhe` concern that check was added for in the first place (see the `Pedido.endereco` fix, 25/07). **Fix, in both places:** `usuario` is now `read_only` on `PedidoSerializer` (`pedidos/serializers.py`) — same root-cause fix as `Endereco.usuario`. `PedidoViewSet.perform_update()` (`pedidos/views.py`) was added — it didn't exist before — replicating `perform_create()`'s `endereco`-ownership check (checked against `serializer.instance.usuario`, the Pedido's *existing* owner, not `self.request.user`, so a staff member fixing a customer's order can still attach an address belonging to *that customer*; same reasoning as `EnderecoViewSet.perform_update()`) and re-asserting `usuario=serializer.instance.usuario` on save as defense in depth, same pattern as that same method. `PedidoAdmin.get_readonly_fields()` marks both `usuario` and `endereco` readonly when `obj is not None` — conditional, like most of the fixes above, but for a different reason this time: both fields are `null=True, blank=True` on the model, so an unconditional readonly wouldn't have broken anything technically, but per the user, picking the customer/address is a real part of creating a `Pedido` by hand in the admin (e.g. a phone order), so the conditional was kept deliberately, not out of necessity. Verified via curl on both surfaces: **API** — as the Pedido's own owner, a `PATCH` forging `usuario` to another user's id returned `200` with `usuario` unchanged (silently ignored, confirming the read-only fix); a `PATCH` with `endereco` set to another user's address id returned a clean `403`; the same `endereco` set to the caller's *own* address succeeded normally; as staff, the same cross-user `endereco` assignment succeeded (bypass, matching `perform_create()`'s existing staff behavior) while `usuario` still stayed the *original* owner's id, not the staff member's own. **Admin** — the existing-Pedido change page renders both `usuario` and `endereco` as readonly links, not `<select>`s; the add page still has both as editable dropdowns; a `POST` to the change endpoint forging both to different ids left both unchanged while `status`, sent in the same request, updated normally. **Fixed 2026-07-27 — a confirmed, real data-integrity incident, structural not just an admin gap: `ItemPedido.produto_nome`/`produto_tamanho` were derived live, not frozen at sale time, so editing a `Variacao` after the fact silently rewrote historical orders.** Every other fix in this file so far has been "field editable in the admin without `readonly_fields`" — this one is different in kind: the bug wasn't (only) that `Variacao.produto`/`Variacao.tamanho` were editable, it's that **`ItemPedidoSerializer` had no columns of its own to protect** — `produto_nome`/`produto_tamanho` were declared as `serializers.CharField(source="variacao.produto.nome", read_only=True)` / `source="variacao.tamanho"`, meaning every time an order was read, those two values were recomputed *at read time* from whatever the linked `Variacao` currently pointed to — not stored anywhere on the `ItemPedido` itself, unlike `preco_unitario`, which was already correctly persisted as a real column. **This is the general distinction that matters for e-commerce historical data: a "derived/computed field" (a live join, re-evaluated on every read) is correct for data that's supposed to always reflect the current state of some other row — but a *sale* is a point-in-time fact, not a live view of the product catalog. `Pedido.total`/`ItemPedido.subtotal` are legitimately derived-then-persisted (recomputed by a signal whenever their inputs change, but the *inputs* — `quantidade`, `preco_unitario` — are themselves already frozen), whereas `produto_nome`/`produto_tamanho` were being derived from a row (`Variacao`) explicitly designed to be mutable long after the sale — inventory gets restocked, products get relabeled, a variant gets reassigned to a different product entirely. Nothing about placing an order should make a `Variacao` immutable in general — the sale needs its own copy of "what was actually bought," a snapshot, exactly like `preco_unitario`.** **Confirmed as a real incident, not just a theoretical risk:** reassigning a `Variacao`'s `produto` from "ADS COLOR" (R$1000) to "Camisa Teste" made a real, already-placed R$1000 order for "ADS COLOR" start displaying as "Camisa Teste" — same price, wrong product, no error, no warning; reproduced again here via curl (see below) to verify the fix. **Fix, four parts:** (1) `ItemPedido` (`pedidos/models.py`) gained real `produto_nome = CharField(max_length=100, null=True, blank=True)` and `produto_tamanho = CharField(max_length=3, null=True, blank=True)` columns (migration `0009_itempedido_produto_nome_itempedido_produto_tamanho`) — nullable because there's no way to know, retroactively, what a *pre-existing* `ItemPedido`'s product/size actually were at the time of that sale; backfilling from the *current* `Variacao` was deliberately not done, since that's exactly the bug being fixed (it would fabricate a plausible-looking but potentially-wrong value for old rows instead of honestly leaving them blank — old orders placed before this fix simply show no product name/size in the API response now, rather than a guess). (2) Both places an `ItemPedido` is created now set both fields explicitly, in the same call as `preco_unitario` — `ItemPedidoViewSet.perform_create()` and the `itens_criacao` loop in `PedidoViewSet.perform_create()` (`pedidos/views.py`) — from `variacao.produto.nome`/`variacao.tamanho` at that exact moment, never touched again after. (3) `ItemPedidoSerializer` (`pedidos/serializers.py`) no longer declares `produto_nome`/`produto_tamanho` with `source=` — they're real `ItemPedido` fields now, so `ModelSerializer` picks them up automatically from `Meta.fields`, and both were added to `read_only_fields` alongside `preco_unitario`/`subtotal` (same rule: always backend-set, never client-set). (4) The API response field names are unchanged (`produto_nome`, `produto_tamanho`), only where the backend sources them from changed, so `src/pages/PedidoDetalhe.jsx` (the only frontend consumer) needed no changes at all — confirmed by reading it, not just assuming. **Admin lockdown, so this doesn't just get worked around at the source:** `VariacaoAdmin` (`produtos/admin.py`) gained `get_readonly_fields()` marking `produto`/`tamanho` readonly when editing an *existing* `Variacao` (`obj is not None` — neither has a default, so unconditional would break creating a new one), and `VariacaoInline` (on `ProdutoAdmin`) gained the same treatment for `tamanho` — `produto` there was already structurally excluded from the inline form regardless (Django auto-excludes the FK-to-parent, confirmed via curl: it renders as `<input type="hidden">`, never a `<select>`, in every row, old or new), so only `tamanho` needed the fix, with the same "add another" trade-off already accepted for `ItemPedidoInline` elsewhere in this file. **Verified via curl, reproducing the exact incident end to end:** created a `Produto` "ADS COLOR" (R$1000) with a `Variacao`, placed an order for it (`produto_nome` correctly `"ADS COLOR"` in the response) — then reassigned that same `Variacao` to a different `Produto` ("Camisa Teste") and a different `tamanho`, directly via the ORM (simulating any bypass of the new admin lock, not just testing the lock itself). Re-fetched the original order: still `"produto_nome": "ADS COLOR"`, `"produto_tamanho"` still the original size — unchanged, confirmed both via the API response and a direct DB read of the `ItemPedido` row. Placed a *second*, brand-new order for the same (now-reassigned) `Variacao` immediately after: correctly showed `"Camisa Teste"` and the new size, proving the fix freezes each sale's *own* snapshot rather than freezing the `Variacao` globally. Then verified the admin lock itself: `VariacaoAdmin`'s change page renders `produto`/`tamanho` as readonly links/text, the add page keeps both editable, and a forged `POST` to the change endpoint (attempting to reassign back) left both unchanged while `estoque` in the same request updated normally; same pattern confirmed for `VariacaoInline` via a `POST` to the parent `Produto`'s own change page. **Fixed 2026-07-27 (closing a gap left by the fix above) — `produto_nome`/`produto_tamanho` were still free-typed text on `ItemPedidoAdmin`'s own *add* form, unrelated to whatever `Variacao` was actually picked.** The fix above made the two fields a real, frozen-at-creation snapshot instead of a live derived value — but it left them in `ITEM_PEDIDO_CAMPOS_CALCULADOS`, the *conditional* readonly list shared with `preco_unitario`/`subtotal` (readonly only when `obj is not None`), which meant a staff member creating a brand-new `ItemPedido` could pick `Variacao` "ADS COLOR - M" from the dropdown while typing "Camisa Teste" into `produto_nome` by hand — a mismatch baked in at the moment of creation, not just an edit-time risk like the fields it was grouped with. `preco_unitario`/`subtotal` genuinely need to stay editable on add (nothing auto-fills them without extra code), but `produto_nome`/`produto_tamanho` should *never* be typed, not even on creation — they're supposed to always be a direct, mechanical copy of the chosen `Variacao`'s own `produto.nome`/`tamanho`. **Fix:** a new `ITEM_PEDIDO_CAMPOS_SEMPRE_DERIVADOS = ["produto_nome", "produto_tamanho"]` constant (`pedidos/admin.py`) is set as the *unconditional* base `readonly_fields` on both `ItemPedidoAdmin` and `ItemPedidoInline` — not gated by `obj is not None` like every other conditional list in this file, since there's no legitimate reason to ever hand-type these two. `readonly_fields` alone only stops typing, though — it doesn't populate the field for a new row (Django just excludes a readonly field from the form entirely, leaving the model instance's blank default), so two more overrides do the actual deriving: `ItemPedidoAdmin.save_model()` sets `obj.produto_nome`/`obj.produto_tamanho` from `obj.variacao.produto.nome`/`obj.variacao.tamanho` whenever `obj.variacao_id` is set, before calling `super().save_model()` — covering the standalone add/change page. `PedidoAdmin.save_formset()` (new — `ModelAdmin`'s default is just `formset.save()`) does the same for `ItemPedidoInline`, the only inline on `PedidoAdmin`: calls `formset.save(commit=False)`, derives both fields on each returned instance, then saves — this is what makes creating a new `ItemPedido` via "Add another" on a `Pedido`'s own *add* page work correctly (the one place this inline still allows creating a new row at all, per the earlier fix — on an *existing* Pedido every inline field is readonly, `variacao` included, so no new row can be created there regardless). Both derive unconditionally, on every save (add and edit alike), not just on creation — belt-and-suspenders against a forged payload the same as against a blank one; on edit this is idempotent today, since `variacao` is already readonly there too (`ITEM_PEDIDO_CAMPOS_FK_SEM_VALIDACAO_NA_EDICAO`), so there's no *different* `variacao` to re-derive from than the one already on record — but it does mean a future change that made `variacao` editable again would need to revisit this comment too, since re-deriving on every save would then silently overwrite `produto_nome`/`produto_tamanho` to match whatever `variacao` was just reassigned to, which is a different (and likely still correct) behavior worth being deliberate about, not accidental. Mirrors how `ItemPedidoViewSet.perform_create()` already derives the same two fields from `variacao` at the API level. **Verified via curl:** the standalone add page has no `<input>` for either field at all (confirmed by checking for the literal tag, not just visual inspection); creating a new `ItemPedido` choosing a real `Variacao` and sending *no* `produto_nome`/`produto_tamanho` in the payload correctly persisted both, matching that `Variacao`'s `produto.nome`/`tamanho`; a second creation attempt that *did* forge mismatched values for both fields in the raw POST payload (bypassing what the rendered form would even allow) still resulted in the correct, `Variacao`-derived values being stored — the forged text was completely discarded. The same forged-payload test repeated through `ItemPedidoInline`, by POSTing to `PedidoAdmin`'s own *add* page with a new inline row (`variacao` set, `produto_nome`/`produto_tamanho` forged), confirmed `save_formset()` works the same way — correct derived values stored, forged ones discarded, while `quantidade` (still legitimately editable) was applied as sent. **Fixed 2026-08-01 — `Pedido.frete_valor`/`frete_nome`/`frete_transportadora`/`frete_prazo_dias` had the exact same admin gap as `preco_unitario`/`subtotal`/`total`/`produto_nome`/`produto_tamanho` above, just discovered later because the fields themselves are newer:** all four are always backend-set from `frete_selecionado` at checkout (`PedidoViewSet.perform_create()`, see "SuperFrete Shipping Integration") and `read_only` on `PedidoSerializer` for the same reason `preco_unitario`/`produto_nome` are — they're meant to be a frozen snapshot of the SuperFrete quote actually charged for that specific order, not a live value. But they were added to the model 29/07 (migration `0010_pedido_frete_nome_pedido_frete_prazo_dias_and_more`), a full three days after `PedidoAdmin.get_readonly_fields()` was already written to lock down `usuario`/`endereco` (27/07, above) — the new fields just never got folded into that method, so they stayed as plain editable `NumberInput`/`TextInput` widgets with no `readonly_fields` coverage at all, letting a staff member rewrite an already-placed order's freight amount or carrier by hand, same class of gap as every other entry in this section, just on a field that didn't exist yet when the pattern was first applied. **Fix:** `PedidoAdmin.get_readonly_fields()` (`pedidos/admin.py`) now also returns `frete_valor`/`frete_nome`/`frete_transportadora`/`frete_prazo_dias` alongside `usuario`/`endereco` when `obj is not None` — same single conditional, no new method needed. Conditional rather than unconditional for the same reason as `usuario`/`endereco`: all four are `null=True, blank=True` on the model, so an unconditional readonly wouldn't break anything technically, but there's no real SuperFrete integration wired into the Admin to auto-fill them, so a staff member building a phone order by hand in the admin still needs to be able to type in a freight amount/carrier at creation time — only editing an *existing* order's snapshot is locked down. Verified via curl: the change page for an existing `Pedido` (with a real SuperFrete snapshot from checkout — `frete_valor=103,88`, `frete_nome=PAC`, `frete_transportadora=Correios`, `frete_prazo_dias=6`) renders all four as `<div class="readonly">` text, no `<input>` elements anywhere in the page for any of the four field names; the add page still renders all four as editable (`<input type="number" name="frete_valor">`, `<input type="text" name="frete_nome">`, `<input type="text" name="frete_transportadora">`, `<input type="number" name="frete_prazo_dias">`); a `POST` to the change endpoint forging all four (`frete_valor=99999.99`, `frete_nome=FORJADO`, `frete_transportadora=FORJADO_TRANSP`, `frete_prazo_dias=999`) returned a normal `302` redirect (no form errors) but left the stored row completely unchanged (`103.88`/`PAC`/`Correios`/`6`, confirmed via a direct DB read after the request), with `status` in the same request applying normally, confirming the rest of the form still works. **Fixed 2026-08-01 — a real `IntegrityError` 500, not just a UX rough edge, introduced as a side effect of the `VariacaoInline.tamanho` readonly fix (27/07, above):** once `tamanho` became readonly on an *existing* `Produto`'s inline (`obj is not None`), the inline's `extra = 3` blank rows kept rendering underneath the real, locked variações anyway — nothing about the readonly fix touched how many *new* rows the formset offered, only whether existing ones could be edited. But a readonly field renders with no `<input>` at all, so those 3 blank rows had no way to ever receive a `tamanho` value — trying to save one (even by just clicking "Salvar" with a row otherwise untouched, since Django's `ModelForm` still attempts to build a `Variacao` from any row with other non-empty defaults) meant submitting a `Variacao` with an empty `tamanho`, and with more than one such blank row present at once, several empty-`tamanho` attempts collided with each other on `unique_together = ["produto", "tamanho"]` before ever reaching a friendlier validation message — a staff member doing something that looked like normal use (viewing/saving an existing product's page) could trigger an unhandled 500 with no indication why. The fix three weeks earlier had only ever addressed *editing* an existing row (`get_readonly_fields()`), never noticed that the same inline still visibly, but silently-brokenly, offered to *create* new ones underneath. **Fix:** `VariacaoInline` (`produtos/admin.py`) gained `get_extra()`, returning `0` when the parent `Produto` already exists (`obj is not None`) and the normal `self.extra` (still `3`) otherwise — no blank rows are rendered at all once there's nothing they could successfully save into, while a brand-new `Produto`'s add page keeps prefilling 3 rows to create a product with a few sizes in one go, the actual working use case `extra=3` exists for. Paired with `has_add_permission()`, also new, returning `False` under the same `obj is not None` condition: `get_extra()` alone stops the blank rows from being *pre-rendered*, but Django's inline template independently renders a "+ Adicionar outro(a) Variação" link/empty-form-template whenever the inline reports it can add — leaving that hidden mechanism enabled would still invite a staff member to manually add a row via that link and hit the exact same failure, just one click later instead of by default. Creating a new size for an existing product still works — through the standalone `Variacao` "Adicionar" page (`VariacaoAdmin`), which was never affected by any of this (its `tamanho` field only becomes readonly when editing an *existing* `Variacao`, same as `VariacaoInline`, but it doesn't carry the extra-blank-rows concept at all). Confirmed via curl: the change page for an existing `Produto` (id 34, 4 real `Variacao` rows) renders `variacoes-TOTAL_FORMS=4`/`INITIAL_FORMS=4` — no extra rows appended — and has zero occurrences of the `__prefix__` empty-form template Django uses to power "Add another" (present 8 times on the add page for comparison), confirming the add affordance is gone at the template level, not just visually suppressed; the add page for a brand-new `Produto` still renders `variacoes-TOTAL_FORMS=3` with all 3 rows' `tamanho` as real editable `<input>` elements, unchanged. A forged `POST` to the existing Produto's change endpoint, manually adding a 5th form (`variacoes-4-tamanho=XXL`, no `id`, alongside the 4 real rows) and inflating `TOTAL_FORMS`/`MAX_NUM_FORMS` in the payload to values that would normally permit it, still returned a clean `302` with no server error — but a direct DB read afterward showed the `Produto` still had exactly its original 4 `Variacao` rows, nothing new created; tracing why confirmed this isn't specific to this fix but a pre-existing Django admin guarantee being exercised correctly: `has_add_permission()` returning `False` makes Django's own `get_inline_instances()` (`django/contrib/admin/options.py`) set `inline.max_num = 0` on the instance regardless of what a client submits in the `MAX_NUM_FORMS` hidden field, and the inline formset's `has_changed()` override explicitly refuses to save any *new* (adding) row once `can_add` is `False` — so the forged 5th row was rejected at the form level before ever reaching the database, independent of the `unique_together` collision this fix set out to prevent in the first place; confirms no security regression, only the intended UX/500 fix. A follow-up creation test (new `Produto`, one filled `Variacao` row) confirmed the create-together-with-a-new-product flow still works end to end, unaffected.

## Backend quirks discovered while building the checkout flow (resolved)

Movido da seção "Backend quirks discovered while building the checkout flow" do CLAUDE.md — o único item que permanece lá é a pendência ainda em aberto (o campo vestigial `usuario: user.id` no frontend), já que essa seção existe justamente para separar o que já foi resolvido do que ainda não foi.

- **Fixed 2026-07-24 — was a real IDOR, not just a quirk:** `EnderecoViewSet` didn't override `perform_update()` (only `perform_create()`), and `EnderecoSerializer` had `usuario` as a plain writable field. Since `IsDonorOrStaff`'s object-level check only confirms the caller owns (or is staff for) the address being edited — it says nothing about what *values* can be written — any authenticated user could `PUT`/`PATCH` `/api/enderecos/{id}/` on their own address with `usuario: <outro_id>` in the body and reassign that address to another user's account. This only affected direct API use (curl/Postman/etc) — the frontend never sent `usuario` on edit (see below), so the UI itself couldn't trigger it. **Fix:** `usuario` is now `read_only` on `EnderecoSerializer` (`pedidos/serializers.py`) — the root-cause fix, chosen over a model-level `blank=True`/`null=True` change because (a) it needs no migration, (b) it's semantically correct (an `Endereco` should never actually have a null owner — the model constraint should stay required), and (c) `blank=True`/`null=True` alone wouldn't have closed the vulnerability anyway, since it only affects requiredness/nullability, not writability — a still-writable field remains just as attackable. `EnderecoViewSet.perform_update()` (`pedidos/views.py`) was also added, re-asserting `serializer.instance.usuario` on every save as defense in depth (technically redundant once the field is read-only, since DRF excludes read-only fields from `validated_data` entirely, but cheap insurance if the serializer ever changes). Manually verified via curl: authenticated as user A, a `PUT` (all required fields + `usuario: <user B's id>`) and a `PATCH` (`{"usuario": <user B's id>}`) against user A's own address both returned `200` with the edit applied, but `usuario` stayed A's id in both cases. **Fixed again, 2026-07-27 — same hole, different door:** the API-level fix above never touched the Django Admin, and an audit of every `ModelAdmin` in the project (prompted by the `ItemPedido`/`Pedido` admin-integrity fixes below) found `EnderecoAdmin` (`pedidos/admin.py`) had no `readonly_fields` at all — `usuario` was a plain editable dropdown in the change form, so a staff member could reassign an `Endereco` (and its whole `Pedido` history via `Pedido.endereco`) to a different user directly through the admin, completely bypassing the `read_only`-on-the-serializer protection above, which only ever covered the API. **Fix:** `EnderecoAdmin.get_readonly_fields()` now marks `usuario` readonly *only when editing an existing `Endereco`* (`obj is not None`) — same conditional shape as `ITEM_PEDIDO_CAMPOS_CALCULADOS` (see the Django Admin section below), because `Endereco.usuario` has no default and isn't nullable (`models.ForeignKey(User, on_delete=models.CASCADE)`), so an unconditional readonly would break creating a new `Endereco` via the admin. Confirmed via curl: the existing-address change page renders `usuario` as readonly text (a link to the linked `User`'s own admin page — Django's default rendering for a readonly FK), not a `<select>`; a `POST` to the change endpoint with a forged `usuario` (a different user's id) left it unchanged while other, genuinely-editable fields in the same request (`rua`, `numero`) updated normally; the add page still has an editable `usuario` field, and a `POST` there successfully created a new `Endereco` for the specified user, confirming admin-based address creation still works.

- **Fixed 2026-07-25:** `Pedido` previously had no FK to `Endereco` at all, so the address collected/created at checkout was saved to the user's account (reusable later) but wasn't linked to the specific order it was entered for. **Fix:** added `Pedido.endereco` (`pedidos/models.py`, migration `0008_pedido_endereco`) — `ForeignKey("Endereco", on_delete=models.PROTECT, null=True, blank=True, related_name="pedidos")`. `PROTECT` (not `SET_NULL`/`CASCADE`) because a historical order's shipping address must never silently disappear or drag the whole order down with it — same reasoning already used for `ItemPedido.variacao`. `null=True, blank=True` because it's a new field on an existing table — pre-existing `Pedido` rows have no address to backfill, and making it required would need a data migration with no real address to put there. Note this is a live FK, not a snapshot: if a user later edits the linked `Endereco` via `MeusEnderecos.jsx`, the order's displayed address changes too, since `endereco_detalhe` always reflects the current row — full point-in-time immutability would need copying the address fields onto `Pedido` at order time instead of referencing them, which is out of scope for this fix. `PedidoSerializer` now exposes both `endereco` (writable id, via `criarPedido({ endereco })`) and `endereco_detalhe` (nested, read-only, `source="endereco"`) — mirroring how `itens` is nested-read/separately-written. `PedidoViewSet.perform_create()` was extended to 403 a non-staff request whose `endereco` belongs to a different user (see above) — this check didn't exist before because the field didn't exist; it closes the same class of IDOR fixed on `EnderecoViewSet` itself, at the point the FK was introduced, rather than shipping it and fixing it later.

- **Fixed 2026-07-27 — quirk introduced by the `Pedido.endereco` fix above:** `EnderecoViewSet` didn't catch `ProtectedError`, so `DELETE /enderecos/{id}/` on an address linked to any `Pedido` (via the `PROTECT` FK) raised an unhandled 500 instead of a clean 400. **Fix:** `EnderecoViewSet.perform_destroy()` (`pedidos/views.py`) now wraps `instance.delete()` in `try`/`except ProtectedError`, re-raising as `rest_framework.exceptions.ValidationError({"detail": "Este endereço não pode ser excluído porque está vinculado a um ou mais pedidos."})` — same `{"detail": ...}` shape as the `diminui_estoque` fix above, and the same reasoning for why (DRF's `exception_handler` only produces that shape for a dict-wrapped `detail`; a bare string gets coerced into a raw JSON list instead). No propagation surprises here: `ProtectedError` is raised directly by `instance.delete()` inside `perform_destroy()`, itself called synchronously from `DestroyModelMixin.destroy()` within the view's own call stack — not from a signal — so there was never a question of whether the exception would reach DRF's handler. Verified via curl: created an `Endereco` linked to a `Pedido` and one unlinked; `DELETE` on the linked one now returns a clean `400` with the message above and the address row remains in the database (confirmed via shell), while `DELETE` on the unlinked one still returns `204` and actually removes the row. `MeusEnderecos.jsx`'s delete-error handler was updated to prefer `error.response?.data?.detail` over its generic fallback (same pattern as `Checkout.jsx`), so the precise message now reaches the user instead of the generic "Tente novamente."

- **Fixed 2026-07-26:** `diminui_estoque` (`pedidos/signals.py`) used to raise a bare `ValueError` on insufficient stock, so `POST /itens/` returned an unhandled 500 (HTML error page) instead of a clean 400. **Fix:** it now raises DRF's `rest_framework.exceptions.ValidationError({"detail": "Estoque insuficiente. Restam apenas N unidades."})` — the `detail` is wrapped in a dict rather than passed as a bare string, because `ValidationError.__init__` coerces any non-dict/non-list detail into a bare list (`["msg"]`), which DRF's exception handler then returns as a raw JSON array instead of `{"detail": "msg"}"`; wrapping it keeps the shape consistent with every other error in this API (e.g. `PermissionDenied` usages in `views.py`), which is what the frontend already expects. Verified via curl (login, create a `Pedido`, `POST /itens/` with `quantidade` > `estoque`) that this reaches the client as a real `400` with `{"detail": "Estoque insuficiente. Restam apenas 3 unidades."}` — signals are sent synchronously (`Signal.send`, not `send_robust`) from within `instance.save()`, which itself runs inside the view's call stack, so an exception raised in a `post_save` receiver propagates through DRF's `dispatch()` exception handling exactly like one raised directly in a view. **However, propagating the right status code wasn't the whole story:** since `ATOMIC_REQUESTS` isn't enabled (see `core/settings.py::DATABASES`), `ItemPedido.save()` commits its `INSERT` immediately, *before* the `post_save` signal (and its own separate `@transaction.atomic` block) even runs — so raising from inside the signal returned a correct `400` while silently leaving an invalid `ItemPedido` row committed in the database (confirmed via the same curl reproduction: the over-quantity row existed in `pedido.itens` afterwards, just never reflected in `Pedido.total` since the exception also stops the later `atualiza_total_pedido` receiver from running — `Signal.send` stops calling remaining receivers once one raises). **Root-cause fix:** the authoritative stock check now lives in `ItemPedidoViewSet.perform_create()` (`pedidos/views.py`), raising the same `ValidationError` *before* `serializer.save()` is ever called, so the invalid row is never created at all. `diminui_estoque`'s own check stays in place as a defense-in-depth backstop for creation paths that don't go through this view (e.g. the Django admin's `ItemPedidoInline`) — though note a `rest_framework.exceptions.ValidationError` raised there isn't caught by Django admin's form handling either (it's not `django.core.exceptions.ValidationError`), so an admin-side insufficient-stock save would still surface as an unhandled 500; that's a pre-existing gap (the original `ValueError` had the same problem there) and out of scope for this fix. Re-verified via curl after the `perform_create()` change: the same over-quantity request still returns `400` with the same message, and this time no `ItemPedido` row is created and `Variacao.estoque` is left untouched; a valid follow-up request (`quantidade` within stock) still creates the item, decrements `estoque`, and updates `Pedido.total` correctly. On the frontend, `Checkout.jsx`'s error handling (`error.response?.data?.detail || <generic fallback>`) needed no change — it already preferred `detail` when present, it just never had one to use while the backend returned an HTML 500 body; now that `detail` is populated, the precise message surfaces automatically.

- **Fixed 2026-07-27:** Order creation used to not be atomic — there was no backend endpoint that created a `Pedido` and its `ItemPedido` lines in one transaction, so `Checkout.jsx` created the Pedido first, then looped `criarItemPedido()` per cart line. If an item failed partway (e.g. insufficient stock on one line), the Pedido was left orphaned with only a partial set of items; the frontend mitigated this by calling `deletarPedido(pedido.id)` on a mid-loop failure, swallowing any failure of that cleanup call itself (best-effort, not blocking) — a workaround, not a fix for the underlying partial-failure window. **Fix:** `PedidoSerializer` (`pedidos/serializers.py`) gained a write-only `itens_criacao` field — `ItemPedidoCriacaoSerializer(many=True, write_only=True, required=False)`, each entry `{variacao, quantidade}` — kept as a separate field rather than making the existing `itens` field writable, since `itens` is `ItemPedidoSerializer` built for *reading* an already-persisted line (exposes `id`, `produto_nome`, `subtotal`, etc., none of which make sense on input) and requires a `pedido` that doesn't exist yet at creation time. `PedidoViewSet.perform_create()` (`pedidos/views.py`) pops `itens_criacao` out of `validated_data` (it isn't a real `Pedido` field, so `ModelSerializer`'s default `.create()` would otherwise pass it straight to `Pedido.objects.create(**validated_data)` and raise an unexpected-keyword-argument error) and, inside a single `with transaction.atomic():` block, saves the `Pedido` and then loops the items, creating each `ItemPedido` via `.objects.create()` — which still fires the existing `calcula_subtotal`/`diminui_estoque`/`atualiza_total_pedido` signals unchanged, so subtotal calculation, stock decrementing, and running-total maintenance are all reused as-is, not reimplemented. Before creating each line, the loop re-fetches the `Variacao` fresh from the DB (`Variacao.objects.select_for_update().get(pk=...)` — see the fixed concurrent-request-race quirk below for why `select_for_update()`, not the `PrimaryKeyRelatedField` instance cached in `validated_data` from up-front payload validation) and checks `estoque >= quantidade`, raising the same `{"detail": ...}`-shaped `ValidationError` used elsewhere in this API if not — same authoritative-check-before-create pattern as `ItemPedidoViewSet.perform_create()`, needed here so a repeated `variacao` id within the same batch sees the previous line's decrement rather than the pre-request stock level (the outer `transaction.atomic()` would also roll back correctly if the `diminui_estoque` signal's own check fired instead, since everything in the block — Pedido, prior `ItemPedido`s, prior stock decrements — is part of the same uncommitted transaction, but checking explicitly first keeps both creation paths consistent and names the specific failing item in a batch). **Same endpoint, not a new route:** `POST /pedidos/` now accepts an `itens_criacao` list rather than gaining a separate creation endpoint — creating an order together with its lines is still creating one `Pedido` resource, and a new route would duplicate the ownership/`endereco` checks already in `perform_create()`. At the time of this fix, `itens_criacao` was optional and the old call shape (`POST /pedidos/` with no body, then `POST /itens/` per line) kept working unchanged, since an omitted `itens_criacao` just meant the loop never ran — **that empty-Pedido path was later closed, 30/07, see below:** it turned out to be a leftover of the old flow rather than a real use case, and is now rejected outright. Verified via curl: a 2-item request where the second line's `quantidade` exceeds its `estoque` returns a clean `400` naming that line, and neither the `Pedido` nor the first (individually valid) `ItemPedido` end up in the database, nor is any stock decremented — confirmed by querying the DB directly after the call. A subsequent all-valid 2-item request returns `201` with both lines and the correct summed `total`, and each `Variacao.estoque` is decremented correctly. The address-ownership 403 check was also re-verified working unchanged. On the frontend, `Checkout.jsx` now makes one `criarPedido({ endereco, itens })` call instead of `criarPedido()` + a `criarItemPedido()` loop, and no longer calls `deletarPedido()` on failure — there's no orphaned Pedido to clean up anymore. `criarItemPedido()` and `deletarPedido()` (`pedidos.js`) are now unused by the UI but were kept as direct bindings rather than deleted, since `POST /itens/` and `DELETE /pedidos/{id}/` are still live, supported endpoints — `criarItemPedido()` for a possible future "add a line to an existing order" feature, `deletarPedido()` for a possible future "cancelar pedido" feature.

- **Fixed 2026-07-27:** Stock decrement used to not be safe against concurrent requests for the same `Variacao`. `diminui_estoque` (`pedidos/signals.py`) checked `variacao.estoque < instance.quantidade` and then did `variacao.estoque -= instance.quantidade; variacao.save()` — a plain Python read-modify-write to an absolute value — and none of the three places that read a `Variacao` for a stock check (`ItemPedidoViewSet.perform_create()`, the `itens_criacao` loop in `PedidoViewSet.perform_create()`, and `diminui_estoque` itself) locked the row. Two different clients racing for the last unit(s) of the same `Variacao` could both read the same pre-decrement `estoque`, both pass the check, and both write an absolute new value — a lost update, silently overselling instead of the second request being rejected. **Fix, applied at all three points:** each now does `Variacao.objects.select_for_update().get(pk=...)` instead of trusting an already-resolved (unlocked) `Variacao` instance, and `diminui_estoque`'s actual decrement now uses an atomic conditional update — `Variacao.objects.filter(pk=variacao.pk, estoque__gte=quantidade).update(estoque=F("estoque") - quantidade)` — checking the returned row count, instead of computing the new value in Python and writing it back. `ItemPedidoViewSet.perform_create()` also gained a `with transaction.atomic():` wrap it didn't have before (needed regardless of locking — see below).
  - **`select_for_update()` alone is not sufficient, and this project can prove it today:** `connection.features.has_select_for_update` is `False` on SQLite (confirmed via `manage.py shell`), and Django's SQL compiler gates the *entire* `select_for_update()` code path — including the "FOR UPDATE" clause *and* the "must be inside a transaction" check it would otherwise enforce — behind that feature flag (`django/db/models/sql/compiler.py`). So on SQLite, `.select_for_update()` is a silent no-op: no lock, no error, just a plain `SELECT`, on any backend that doesn't support it. The atomic conditional `.update(estoque=F(...) - quantidade)` is the layer that's actually safe regardless of backend, since the row's current value, the `estoque__gte` condition, and the new value are all evaluated together in one SQL statement — a concurrent writer can't split "check" from "write" apart, which is exactly what the old `variacao.estoque -= quantidade; variacao.save()` pattern allowed. `select_for_update()` is kept anyway (real protection on Postgres/MySQL — the Phase 5 target — and it's what the earlier "known limitation" note singled out), but the `F()` update is the layer this project can actually rely on and verify before that migration.
  - **`ItemPedidoViewSet.perform_create()` needed a new `transaction.atomic()` wrap, not just locking:** without it, a rejection from the now-properly-checked `diminui_estoque` signal (e.g. losing a race) would arrive *after* the `ItemPedido` row's `INSERT` had already committed on its own (same root cause as the orphaned-row bug fixed in the `ValueError`→`ValidationError` entry above, just triggered by a lost race instead of a single over-quantity request) — wrapping the check and `serializer.save()` together means a rejection anywhere in that block rolls back the `INSERT` too. The `itens_criacao` loop in `PedidoViewSet.perform_create()` already had this wrap from when it was built (see the "order creation isn't atomic" fix above), so it only needed the `select_for_update()` change.
  - **No PostgreSQL available to test against** (checked: no `psql`/`postgres` binary, no Docker, no passwordless `sudo` to install it in this environment) — asked the user, who chose to proceed without it rather than install Postgres. Validation instead: (1) static review confirming every `select_for_update()` call sits inside a `transaction.atomic()` block, since Django only *enforces* that requirement on backends where `has_select_for_update` is `True` — SQLite won't raise `TransactionManagementError` even if that nesting were wrong, so this had to be checked by reading the code, not by running it; (2) the existing curl regression suite (single-item creation, insufficient-stock rejection with no orphaned row, the `itens_criacao` atomic batch, both its failure and success paths) re-run and passing unchanged; (3) a real `threading`-based concurrency test (`estoque=1`, two `POST /itens/` requests for `quantidade=1` each, fired at a `threading.Barrier` to maximize simultaneity) — expected, per SQLite's whole-database write-lock, to be inconclusive (unable to distinguish fixed from still-racy code), but turned out not to be: the *old* code's race window sat entirely outside any transaction (the pre-check read `serializer.validated_data["variacao"]`, a plain unlocked Python read, before `serializer.save()` ever opened a transaction), so SQLite's write-lock never protected it. Re-running the exact same test against the unfixed code (via `git stash`) reproduced the overselling bug directly: **2 successes out of 2 requests in 4 of 5 trials**, both writes computing `1 - 1 = 0` independently and one decrement silently vanishing. Against the fixed code, the same test ran **12 times with exactly 1 success every time** — the loser got either a clean `400` or, more often, an unrelated `OperationalError: database is locked` `500` (SQLite's dev-server write-lock timeout under genuinely concurrent threaded requests, not a bug in the fix's logic — confirmed via direct DB inspection after each run: no orphaned rows, no negative stock, no double-decrement in any trial). **What this does and doesn't prove:** it's real evidence the specific exploitable gap in the old code (an unlocked check outside any transaction) is closed, and that the atomic `F()` update behaves correctly under genuine SQLite write contention. It is *not* evidence that `select_for_update()` correctly serializes concurrent transactions under real MVCC/row-level locking, since SQLite never exercises that code path at all (confirmed above) — that guarantee rests on PostgreSQL's documented `SELECT ... FOR UPDATE` semantics plus the static code review, not on anything executable in this environment. Re-verify with an actual concurrency test against PostgreSQL before or during the Phase 5 migration.

- **Fixed 2026-07-30 — a Pedido with zero items was still creatable via `POST /pedidos/`, a leftover gap from the old flow, not a real use case:** the "order creation isn't atomic" fix (27/07, above) made `itens_criacao` optional so the pre-existing "create empty Pedido, then `POST /itens/` per line" flow would keep working unchanged during that migration. That old flow has since been fully replaced — `Checkout.jsx` always sends a non-empty `itens_criacao` (it's had a real cart to build it from since the atomicity fix), and the Django admin creates `Pedido` + `ItemPedido` together through its own form/inline, never through this API (confirmed by reading `pedidos/admin.py`: no HTTP client, no `PedidoViewSet` usage, plain ORM calls) — so an empty/missing `itens_criacao` on `POST /pedidos/` was reachable only via direct API use (curl/Postman/etc), not through anything the product actually does, and stayed reachable purely because nothing had gone back to tighten it. **Fix:** `PedidoViewSet.perform_create()` (`pedidos/views.py`) now checks `itens_criacao` first thing and raises `rest_framework.exceptions.ValidationError({"detail": "Um pedido precisa ter pelo menos um item."})` — same `{"detail": ...}` shape as every other error in this API — before anything is created, if the list is missing or `[]`. Considered and reverted putting this in `PedidoSerializer.validate()` instead: conceptually it's a pure input-shape check with no DB race to protect against (unlike the stock checks in `perform_create()`, which need a freshly locked `Variacao` read), so a serializer validator looked like the more idiomatic fit at first — but DRF's `as_serializer_error()` unconditionally wraps a dict-shaped `ValidationError` raised inside a serializer's `validate()` into `{"detail": [...]}` (a list), confirmed via curl, breaking the bare-string `{"detail": "..."}` shape this API uses everywhere else (e.g. the insufficient-stock check right below it in the same method). Raising directly in the view, like that existing check already does, avoids the wrapping and keeps the two errors byte-for-byte consistent. The field itself (`itens_criacao` on `PedidoSerializer`) stays `required=False` — the check can't be pushed onto the field via `required=True, allow_empty=False` instead, since the same serializer is reused for `PATCH`/`PUT` (`perform_update()`), which never sends or needs `itens_criacao` at all. Verified via curl: `POST /pedidos/` with no body and with `{"itens_criacao": []}` both now return `400` with the message above, and neither request leaves a `Pedido` row behind (confirmed via a direct DB read); a normal request with a real item still returns `201` with the item, correct `total`, and the expected stock decrement; a `PATCH` on an existing Pedido that only changes `status` (no `itens_criacao` in the payload at all) still succeeds unchanged, confirming updates weren't affected.

### `Variacao.tamanho` — incidente de ordenação e sua correção (10/08)

- **`Variacao.tamanho`'s display order — fixed 10/08, real bug, not a hypothetical.** `tamanho` is a plain `CharField(max_length=3)`, free text — no `choices=`, no numeric field, nothing at the DB level distinguishing a shoe size ("38") from a clothing size ("GG") or "U" (tamanho único). Reported symptom: on `ProdutoDetalhe.jsx`, a shoe product's size buttons could show "38" *after* "44". **Root cause, confirmed by reading the code, not assumed:** neither `ProdutoDetalhe.jsx` (`produto.variacoes.map(...)`, no `.sort()` anywhere in that file) nor the backend (`Variacao` has no `Meta.ordering`; `ProdutoViewSet.get_queryset()`'s `.prefetch_related("variacoes")` has no `.order_by()`; `VariacaoSerializer`/`ProdutoSerializer` applied no ordering either) sorted `variacoes` *at all* — the list was rendered in whatever order the DB returned it, which for an unordered query is effectively insertion order (the order each `Variacao` row was created). This is a subtly different bug than "alphabetical sort" (the initial hypothesis going in): a lexicographic string comparison of same-length two-digit numbers like `"38"` and `"44"` actually already sorts correctly (`"3" < "4"`) — the real failure mode is that sizes created out of sequence (e.g. a missed size added later by hand through the Django Admin, after the others already existed) simply stay wherever they were inserted, regardless of their numeric value. **Confirmed with a real product already in this state, not a synthetic example:** `Produto` id 199 ("Tenis Nike Air Force") has its "37" `Variacao` row created *after* "38"–"44" (`Variacao.id` 1169 vs. 329–335) — before the fix, `GET /api/produtos/199/` returned `["38", "39", "40", "41", "42", "43", "44", "37"]`, reproducing the reported symptom exactly (just with "37" trailing instead of "38", the same class of bug). **Fix:** `produtos/models.py::chave_ordenacao_tamanho(tamanho)`, a module-level sort-key function (not a DB `ORDER BY`, see below) with a documented 3-way precedence — purely numeric values (shoe sizes) sort by integer value; a recognized clothing size (`ORDEM_TAMANHOS_ROUPA = ["P", "M", "G", "GG", "XG"]`, a small list module-level constant *next to* the function) sorts by its position in that list, not alphabetically (would be wrong for `GG`/`XG` — alphabetically `"GG"` sorts before `"M"`, which is wrong); anything else (`"U"`, or an unrecognized value) sorts last, alphabetically among itself. `ProdutoSerializer.variacoes` changed from a plain nested `VariacaoSerializer(many=True, read_only=True)` to a `SerializerMethodField` (`get_variacoes()`) that sorts `obj.variacoes.all()` with this key before serializing — reuses `ProdutoViewSet`'s existing `prefetch_related("variacoes")` cache, no extra query per product. **Deliberately a Python sort key, not `Meta.ordering`/`.order_by("tamanho")` on the DB side:** a DB-level `ORDER BY` can trivially do numeric-as-text or alphabetical, but not "P before M before G before GG before XG" without a database-specific `CASE WHEN` expression, and would need to special-case numeric-vs-letter values differently depending on the DB engine (SQLite's implicit `CAST` behaves differently from Postgres's, and this project is moving from SQLite in dev to Postgres in production per "Development Status" below) — a plain Python function sorting an already-fetched, already-small list (a handful of `Variacao`s per `Produto`) avoids that portability risk entirely for negligible cost. **`ORDEM_TAMANHOS_ROUPA` is a deliberate, minimal duplication of `TAMANHOS_ROUPA` in `produtos/management/commands/seed_produtos.py`, not an import from it** — unlike `aplicar_variacoes_padrao.py`/`completar_marcas_por_categoria.py` (which already import `CATEGORIAS_CONFIG` from that same module), those are one-off management commands; `chave_ordenacao_tamanho()` runs on every `GET /produtos/` request, and importing a `management/commands/` module — meant to be an optional, manually-invoked script — into request-path code is the wrong dependency direction. The two lists must be kept in sync by hand if a new clothing size is ever added; flagged in a comment on `ORDEM_TAMANHOS_ROUPA` itself. **Verified against the real dev DB, not just unit-level:** `GET /api/produtos/199/` (both directly and via the `/api/produtos/?search=` list endpoint) now returns `["37", "38", ..., "44"]`, correctly ordered, with the underlying DB rows *unchanged* (still `id` order `329..335, 1169` — the fix sorts on read, not by rewriting stored data). The clothing-size branch was verified at the function level (no naturally out-of-order clothing product exists in the current dev DB to reproduce against directly): shuffled `["GG", "M", "G", "XG", "P"]` sorts to `["P", "M", "G", "GG", "XG"]`; shuffled numeric sizes `["44", "38", "9", "40"]` sort to `["9", "38", "40", "44"]` (proving true numeric, not lexicographic, comparison — a string sort would have put `"38"` before `"9"`); a mixed list `["GG", "44", "U", "38", "P"]` sorts to `["38", "44", "P", "GG", "U"]`, confirming the three groups (numeric / recognized roupa / everything else) never interleave even though no real `Produto` mixes them today.

### InfinitePay — falta de idempotência na geração de link, e o fix (07/08)

- **Fixed 2026-08-07 — no idempotency on link generation, previously a real, unmitigated gap.** `gerar_link_pagamento()` could legitimately be called more than once for the same `Pedido` — the frontend's own "Tentar novamente" retry button (`Checkout.jsx`, see below) re-calls it with the same `pedidoCriadoId` on a failed attempt, and nothing stopped a client from calling it again on a *successful* prior attempt either. Every call independently created a brand-new InfinitePay checkout link via `POST /links`, with no check for a still-valid link already existing for this `Pedido` — meaning multiple distinct, simultaneously valid checkout links could exist for the same order, and since `payment_check`/the webhook only confirm that *some* transaction for that `order_nsu` was paid the expected amount (not that only one payment ever happens), more than one of those links actually getting paid (double-click, a leaked/reused old link, a webhook retry racing a second manual payment) would go financially unnoticed by this codebase — `Pedido.status` only flips once, but each payment still completes for real on InfinitePay's side, discoverable only by reconciling against InfinitePay's own dashboard. **Re-confirmed before fixing, not assumed: no expiration or invalidation mechanism for a checkout link is documented by InfinitePay.** Checked both places named in the original note — the technical API reference (`docs.infinitepay.io`, and the same host `api.checkout.infinitepay.io/docs` and `api.infinitepay.io/docs` both 301-redirect to) could not actually be reached (`getaddrinfo ENOTFOUND`, consistent across many retries and several guessed paths — the domain simply doesn't resolve from this environment right now, not a 404 or an auth wall) — and the Central de Ajuda (consumer help center), which *was* reachable: searched directly for link expiration/cancellation and read the two main articles on using Link de Pagamento ("Como usar o Link de Pagamento?", "Como fazer uma venda com o Link de Pagamento?") plus a search for "cancelar cobrança" — none mention automatic expiration, and the only link-management feature described (`Histórico` under the `Vender` menu) is explicitly read-only consultation of past links, not cancellation/deactivation. Not a hard proof at the API level (the technical reference genuinely couldn't be reached this pass), but consistent with, and no weaker than, the original unresearched assumption — and the product itself exposing no such concept to end users is real evidence against a hidden API-level one. **Fix:** new `Pedido.link_pagamento_url` column (`URLField(null=True, blank=True)`, migration `0011_pedido_link_pagamento_url`, `pedidos/models.py`) caches the checkout URL InfinitePay returns. `gerar_link_pagamento()` (`pedidos/views.py`) now checks it immediately after the existing `status != "novo"` guard: if already set, returns it directly (`Response({"url": pedido.link_pagamento_url})`) with **no call to `criar_link_pagamento()`/InfinitePay at all**; otherwise the flow is unchanged, and the URL is persisted (`pedido.link_pagamento_url = url; pedido.save(update_fields=["link_pagamento_url"])`) right before returning it for the first time. **Validity is tied to `Pedido.status`, deliberately not to time** — no new expiration/expiry-date field: the existing `status != "novo"` guard already blocks generating (or now, reusing) a link the moment the order leaves `"novo"` (paid or cancelled), which is exactly when a cached link stops being relevant; nothing about the fix needed to know when a link itself expires, since InfinitePay was reconfirmed above to document no such thing. Same pattern as `frete_valor`/`frete_nome` etc: `null=True, blank=True`, no backfill for pre-existing `Pedido` rows (they simply generate and cache a link on first real call, same as any row created after this fix). `PedidoAdmin.readonly_fields` (`pedidos/admin.py`) now also includes `link_pagamento_url`, unconditionally (not gated by `obj is not None` like `usuario`/`endereco`/the `frete_*` fields) — unlike those, there's no legitimate reason for a staff member to ever hand-type a payment link, on a new `Pedido` or an existing one, so there's no add-time use case to preserve; safe unconditionally the same way `total` already is, since the field is nullable with no default. **This does not address the two other, separate gaps already on record for this integration** (see the callouts at the top of this section and under "Webhook" below): the webhook's real end-to-end delivery path is still unverified, and `INFINITEPAY_HANDLE` still points at the developer's personal dev/test account — neither was in scope here. **Verified via curl against the real InfinitePay API, not mocked** (three consecutive `POST /pedidos/141/gerar-link-pagamento/` calls, logged in as the order's own owner): the first call took 0.53s (a real network round trip to InfinitePay's `POST /links`) and returned a real, working checkout URL (separately confirmed to resolve `200` when fetched); the second and third calls took 0.03s and 0.02s respectively — no InfinitePay round-trip, consistent with hitting the DB cache instead — and returned the *exact same* URL string as the first call, byte for byte; a direct DB read after confirmed `Pedido.link_pagamento_url` held that same URL. Separately verified the status guard still works even with a link already cached: manually flipped the same Pedido's `status` to `"confirmado"` (bypassing the API, since there's no legitimate way to reach that state without a real completed payment) and confirmed `POST .../gerar-link-pagamento/` still returned a clean `400` with `{"detail": "Este pedido não está aguardando pagamento."}`, unchanged from before this fix — the cached URL does not bypass the guard.
