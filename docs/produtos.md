# docs/produtos.md

> Consulte primeiro `CLAUDE.md` na raiz do repositório — ele explica o índice de documentação, o mecanismo de autenticação (transversal), e o padrão a seguir ao registrar mudanças futuras neste arquivo.

Documentação de domínio: **Categoria, Marca, Produto, Variacao** — o catálogo de produtos, os management commands que o povoam/organizam, e o Django Admin desses models.

## Key Model Relationships

- **Produto** → has many **Variacao** (size variants with stock tracking, CASCADE)
- **Produto** → belongs to **Marca** and **Categoria** (both SET_NULL)
- **Produto** also carries `imagem_url` (`CharField(max_length=255, null=True, blank=True)`, added 08/08, migration `0010_produto_imagem_url`) — a relative path served as a static file by the frontend itself (e.g. `/produtos/CONJUNTO-LACOSTE-2026.jpg`, resolving against `frontend/public/produtos/CONJUNTO-LACOSTE-2026.jpg` — Vite serves anything under `public/` at the matching root path, verbatim, in both `npm run dev` and a production build; confirmed via curl in dev and by inspecting `dist/` after `npm run build`), **not an external URL.** Deliberately `CharField`, not `URLField`: confirmed via `django.core.validators.URLValidator` and `django.forms.URLField` that both flatly reject a schemeless relative path like `/produtos/x.jpg` ("Insira um URL válido.") — `URLField` would silently break the first time this value passed through a `ModelForm` (Django Admin) or a DRF serializer validation path, even though the value is exactly correct for how the app actually serves the image. Populated by `produtos/management/commands/importar_produtos_reais.py` (see below) — a real product image implies a real, but as-yet-unpriced-and-uncategorized, `Produto`.

**Open pendency, not solved yet — these images are local-only, not committed to Git (deliberate, 08/08).** The 115 real product photos backing `imagem_url` today live only in `frontend/public/produtos/` on this developer's machine — saved manually from the client's real online catalog, and deliberately kept out of the repository (the user's own call, confirmed 08/08 when this field was added). Consequences, spelled out rather than left implicit: cloning this repo on another machine gets 116 `Produto` rows whose `imagem_url` points at files that don't exist there; more importantly, **deploying without this folder breaks every product image in production** — the chosen frontend host is Cloudflare Pages (see the "🌐 Infraestrutura & Hospedagem" Notion page under "Alto nível"), which builds straight from the Git source, so a file that was never committed simply isn't there to serve, and every `<img src="/produtos/...">` 404s on the live site even though the DB rows and paths are otherwise correct.

**Committing the folder as-is would not be the real fix either.** 115+ binary image files checked into Git permanently bloat repository history (every future clone/fetch carries that weight forever, unlike a file that's later deleted), with no CDN, resizing, or format optimization — real load-time cost for an e-commerce storefront, not just a git-hygiene concern. **The actual fix was already scoped before this field existed:** the same Notion page has an "🖼️ Imagens de Produto" section, still open as of 30/07 — it notes Neon (the chosen Postgres host) includes no file storage, so product images are "uma peça de infraestrutura separada," and names Cloudinary (free tier, automatic image optimization) as the option considered so far, explicitly left open to alternatives ("vale perguntar para o Mateus se ele tem outra sugestão") — nothing finalized. **Migrating means re-uploading these 115 (and future) images to whichever service is chosen (Cloudinary, Cloudflare R2, S3, or equivalent) and rewriting every `Produto.imagem_url` from a local relative path to that service's real external URL.** At that point `imagem_url` should very likely go back to being a proper `URLField` (or at minimum gain real URL-format validation) — the entire reason it's `CharField` today (`URLValidator` rejecting a schemeless relative path, see above) stops applying once the value is always a real `https://...` URL from an external host.

**This is a hard deploy prerequisite for Phase 5, not an optional polish item** — see "Pendências" below and "Not yet done"/"Development Status" in the root `CLAUDE.md`. The storefront cannot go live with product images that only resolve on one developer's laptop.

Only products created from this point forward have an accurate `criado_em`.

**Added 18/08 — `Favorito` model (`produtos/models.py`, migration `0013_favorito`)** — join table between `User` and `Produto` (`usuario`/`produto`, both `CASCADE`, `unique_together=["usuario", "produto"]` so the same user can't favorite the same product twice; `criado_em`, `Meta.ordering = ["-criado_em"]`). `FavoritoSerializer` nests a full, live `ProdutoSerializer` under `produto` for reads (not a frozen snapshot like `ItemPedido.produto_nome` — a favorito should always reflect the product's current price/stock/image), with a separate write-only `produto_id` (`PrimaryKeyRelatedField`) as the only way to specify which product to favorite; `usuario` isn't a serializer field at all (not even `read_only`, unlike `EnderecoSerializer`) — there's no use case for echoing the owner back in the payload. `FavoritoViewSet` (`ModelViewSet`, `/api/favoritos/`, registered in `produtos/urls.py`) is `IsAuthenticated`-only with no staff branch in `get_queryset()` (unlike `PedidoViewSet`/`EnderecoViewSet`) — favoriting is purely personal, no admin/staff use case exists for seeing another user's favorites through this API. `get_queryset()` filters to `usuario=request.user`; `perform_create()` assigns `usuario` server-side (same IDOR protection as `EnderecoViewSet.perform_create()`) and catches `IntegrityError` from the `unique_together` constraint, re-raising as a clean `{"detail": "Este produto já está nos seus favoritos."}` 400 — same pattern as `EnderecoViewSet.perform_destroy()` catching `ProtectedError`, since DRF's automatic `UniqueTogetherValidator` can't cover this constraint (it needs both fields present and writable on the serializer, and `usuario` is neither). No Django Admin registration — not requested, no staff workflow needs it today. Verified via curl: create (201, nested `produto`), list (200), create-again-same-product (400, clean message, not a 500), delete (204), re-list (empty). Frontend: `src/api/favoritos.js`, a heart-toggle on `ProdutoDetalhe.jsx`, and a new `/meus-favoritos` page — see `docs/frontend.md`.

`produtos/management/commands/importar_produtos_reais.py` — for every image file in `frontend/public/produtos/` (`.jpg`/`.jpeg`/`.png`/`.webp`, case-insensitive), creates one `Produto` with:
  - `nome` derived from the filename: extension stripped, `-`/`_`/`=` treated as word separators (`=` because at least one real file uses it, `CONJUNTO-LACOSTE=DRI-FIT.jpg`), each resulting word passed through `str.capitalize()` (not `.title()` — deliberately, since `.title()` would capitalize the letter right after an apostrophe too, turning `"OVERSIZED'S"` into `"Oversized'S"` instead of the intended `"Oversized's"`). Apostrophes are left as-is, not treated as a separator. No accent recovery — a filename that never had one (e.g. `TENIS`) becomes `"Tenis"`, not `"Tênis"`; that correction, like everything else below, is manual follow-up work.
  - `imagem_url` = `/produtos/<nome-do-arquivo>` (the Vite-served path above).
  - `preco = 0` — an obvious placeholder, not a real price; **`categoria = None` and `marca = None`** (both already nullable on the model, confirmed above) — there's no reliable way to infer either from a filename alone.
  - **No `Variacao` is created.** Tamanho/estoque are real, physical facts (what sizes actually exist, how many of each are in stock) that only the user has — nothing in a product photo's filename can supply them, so every imported `Produto` starts with zero variações and needs them added by hand via the Django Admin (`VariacaoInline` on `ProdutoAdmin`, or the standalone `Variacao` "Adicionar" page) before it's purchasable — a `Produto` with no `Variacao` can't actually be added to a cart (see `ProdutoDetalhe.jsx`: no sizes to select, "Adicionar ao carrinho" stays disabled).
  - Idempotent: looked up by `imagem_url` (a 1:1, deterministic key back to the source file) via `get_or_create`, so re-running the command after adding more images to the folder only creates `Produto`s for the new files, never duplicates existing ones — confirmed by running it twice in a row (115 created, then 0 created / 115 skipped on the second run).
  - Run once against the dev DB on 08/08: 115 image files found, 115 `Produto` rows created (`Produto.objects.count()` went from 1 — just `"ADS COLOR"`, the preserved test row above — to 116). **Full manual cleanup still needed for every one of these 116 rows: real `preco`, `categoria`, `marca`, and at least one `Variacao` per product, all via the Django Admin** — this command only gets a real photo and a legible name into the system, nothing else.

`produtos/management/commands/aplicar_variacoes_padrao.py` — added 08/08, fills in `Variacao`s for products the user has categorized but not yet sized (`Produto.objects.filter(categoria__isnull=False, variacoes__isnull=True)`). Per product, looks up `categoria.nome` in `seed_produtos.py`'s own `CATEGORIAS_CONFIG` dict (imported, not duplicated) for that category's `tabela_tamanhos`, creating one `Variacao` per size with `estoque=10` (placeholder). **Deliberately reuses `CATEGORIAS_CONFIG` rather than re-encoding the categoria→tamanhos mapping a third time in the backend.** A category not in `CATEGORIAS_CONFIG` gets nothing created automatically — listed in the command's own output for manual sizing instead of guessing a shape. Idempotent by construction (the same `variacoes__isnull=True` filter drops a product from scope the moment it has one `Variacao`), plus `get_or_create` per `(produto, tamanho)` as a defensive backstop. `CATEGORIAS_CONFIG` now has an entry for every real `Categoria` in the DB — extended over several passes as the user created new categorias by hand through the Admin faster than the config kept up (`Conjuntos`/`Jeans`/`Polos`/`Bermudas Elastano`/`Sandálias`, then `Relógios`/`Óculos`/`Cintos`/`Carteiras`, then `Shoulder Bag`/`Meias`/`Cuecas` all gained entries over time) — so every `Produto` with a `categoria` set today has at least one `Variacao`. Run-by-run counts and which categories were unrecognized on which pass are in HISTORICO.md.

`produtos/management/commands/completar_marcas_por_categoria.py` — added 10/08, creates brand-new `[TESTE]`-prefixed `Produto` rows (not just fills in existing ones) so the Header's mega menus have full categoria×marca coverage during development/demos. **Development-only — not a merchandising tool, has no role in production.** `MARCAS_ALVO_IDS`: 10 target brands by id (Armani/Balenciaga/Boss/Casa Blanca/Diesel/Gucci/Lacoste/`"Louis Vuiton"` — this brand's real `Marca.nome` has a pre-existing typo missing Vuitton's second "t", deliberately left uncorrected on the `Marca` row itself, so `MARCAS_ALVO_IDS` uses the real misspelled name/Nike/Zara). `_resolver_marcas_alvo()` re-validates every id/name pair on every run, `CommandError`ing loudly (nothing created) if a `Marca` was ever renamed or an id is wrong, instead of silently mis-attaching test products to the wrong brand. Coverage check per categoria×marca pair: counts as "already represented" only if some `Produto` (real or `[TESTE]`) with that exact combo has at least one `Variacao`, source-agnostic. For every still-missing combination, creates one `Produto` named `"[TESTE] {categoria.nome} {marca.nome}"` (the prefix is load-bearing — how these rows are found and bulk-deleted later, `Produto.objects.filter(nome__startswith="[TESTE]")`), with a price from `seed_produtos.py`'s own `gerar_preco()` and `Variacao`s created via the same `CATEGORIAS_CONFIG` lookup `aplicar_variacoes_padrao.py` uses. Idempotent via `get_or_create(nome=...)`, safe even across a mid-run crash. **As of the last run: 260 `[TESTE]` `Produto` rows exist across 18 categorias × 10 marcas** — see "Pendências" below for the production cleanup this requires. - **Variacao** has `unique_together = ["produto", "tamanho"]`; also carries `peso` (kg, `DecimalField(max_digits=5, decimal_places=3)`) and `altura`/`largura`/`comprimento` (cm, `IntegerField`) — added 27/07 for the future SuperFrete shipping-cost integration (see "SuperFrete Shipping Integration" in `docs/pedidos.md`), not consumed by anything yet. Deliberately per-`Variacao`, not per-`Produto`: confirmed as the market-standard approach (Nuvemshop, Shopify both do this) — a product's different sizes can legitimately weigh/measure differently, even though in practice many will end up with similar values. `altura`/`largura`/`comprimento` are `IntegerField`, not `DecimalField`, matching how shipping carriers (Correios/Melhor Envio/SuperFrete) normally declare package dimensions — whole cm, no real need for sub-centimeter precision; `peso` uses 3 decimal places since grams do meaningfully affect a shipping quote. All four have a `default` rather than `null=True`: a shipping calculation always needs *some* value, so an approximate default beats a missing one. Defaults (`peso=0.3`, `altura=3`, `largura=25`, `comprimento=35`) are a placeholder for a typical folded-garment envelope/package — not real per-product measurements, which the client hasn't provided yet; the migration (`produtos/migrations/0009_variacao_altura_variacao_comprimento_and_more`) applied these same defaults to every pre-existing `Variacao` row, so today every variant in the catalog reports the identical placeholder until corrected by hand. `VariacaoSerializer` exposes all four as ordinary writable fields (not `read_only` — unlike `ItemPedido.preco_unitario`, these are real data meant to be corrected once known, not something the backend derives) and both `VariacaoAdmin` and `VariacaoInline` (on `ProdutoAdmin`) expose them as editable — the likely path for filling in real values, but deliberately *not* added to `VariacaoAdmin.list_editable` alongside `estoque`: `estoque` is a live operational number that changes with every sale/restock and benefits from a fast, no-page-load edit from the changelist, while weight/dimensions are physical measurements set once and rarely revisited, better suited to the full change form (all four together, with labels) than a cramped list-view cell. **Possible future improvement, not implemented now:** if manually setting these per `Variacao` turns out to be too repetitive in practice (e.g. most sizes of most products really do share the same weight/dimensions), a natural next step would be letting a `Variacao` inherit a default from its "root" `Produto` and only override when a specific size genuinely differs — not built now since the per-`Variacao` values don't exist yet to observe that pattern from.
- **`Variacao.tamanho`'s display order.** `tamanho` is a plain `CharField(max_length=3)`, free text — nothing at the DB level orders a shoe size ("38") relative to a clothing size ("GG") or "U" (tamanho único). `produtos/models.py::chave_ordenacao_tamanho(tamanho)` is a module-level Python sort key (deliberately not a DB `ORDER BY`/`Meta.ordering` — a "P before M before G before GG before XG" ordering needs a database-specific `CASE WHEN` expression, and this project moves from SQLite in dev to Postgres in production, which handle implicit casts differently) with a 4-tier precedence: purely numeric values (shoe sizes) sort by integer value → range-shaped values like "35-40" (`PADRAO_FAIXA_TAMANHO = re.compile(r"(\d+)-(\d+)")`, matched via `.fullmatch()`, sorted by the first number — used by `Meias`) → a recognized clothing size (`ORDEM_TAMANHOS_ROUPA = ["P", "M", "G", "GG", "XG"]`, by list position, not alphabetically — alphabetical would wrongly sort "GG" before "M") → anything else ("U", or unrecognized), alphabetically among itself. `ProdutoSerializer.variacoes` is a `SerializerMethodField` (`get_variacoes()`) that sorts `obj.variacoes.all()` with this key before serializing, reusing `ProdutoViewSet`'s existing `prefetch_related("variacoes")` cache — no extra query. **`ORDEM_TAMANHOS_ROUPA` is a deliberate, minimal duplication of `TAMANHOS_ROUPA` in `produtos/management/commands/seed_produtos.py`, not an import from it** — `chave_ordenacao_tamanho()` runs on every `GET /produtos/` request, and importing a `management/commands/` module (meant to be an optional, manually-invoked script) into request-path code would be the wrong dependency direction; the two lists must be kept in sync by hand if a new clothing size is ever added, flagged in a comment on the constant itself. Fixed 10/08 after a real out-of-order bug (a "37" `Variacao` created after "38"–"44" rendered last on a real product); the range tier was added later the same day when `Meias` needed it. Full incident reproduction and verification (both additions) in HISTORICO.md.

### Query Optimization

`ProdutoViewSet` uses `select_related("marca", "categoria").prefetch_related("variacoes")` to avoid N+1 queries, with a default `order_by("nome")` so pagination is always deterministic (avoids `UnorderedObjectListWarning`); clients can still override via the `ordering` query param (`ordering_fields`: nome, preco, and — added 13/08 — criado_em). Supports `filterset_fields` (marca, categoria, and — added 13/08 — em_outlet), `search_fields` (nome, marca__nome).

**Customizable page size, added 08/08:** `ProdutoViewSet.pagination_class` is `produtos/pagination.py::ProdutoPagination` (a thin `PageNumberPagination` subclass), not the project-wide `DEFAULT_PAGINATION_CLASS` (fixed `PAGE_SIZE = 10`, `core/settings.py`) — scoped to this one `ViewSet` rather than raising `page_size_query_param` globally, since the Catálogo is the only page with a page-size selector today; every other paginated list (`pedidos`, `enderecos`, ...) still defaults to a fixed 10. `page_size_query_param = "page_size"` lets a client request `?page_size=20`; `max_page_size = 50` caps it server-side regardless of what's requested — confirmed via curl that `?page_size=10000` still returns only 50 results, not the full 51-row dev catalog, so the query param can't be abused to force an unbounded response. Frontend: `Catalogo.jsx` adds a "10/20/50 por página" `Select` next to the existing ordering `Select`, synced to the URL via the `page_size` search param (same `useSearchParams` pattern as every other filter on this page — omitted from the URL entirely at the default value of 10, same as `atualizarFiltro` already does for `ordering`); changing it resets `page` back to 1, same as changing any other filter. `totalPaginas` is now computed from the selected `pageSize`, not a hardcoded constant. `listarProdutos()` (`src/api/produtos.js`) gained an optional `pageSize` param, sent as `page_size` only when provided.

### Mega Menu Navigation (`GET /api/menu/categorias/`)

Added 07/08. Originally backed a single catch-all "Categorias" mega menu (`MegaMenu.jsx`, since replaced — see `docs/frontend.md`); as of the same-day Header redesign, backed the "Roupas" mega menu plus the "Tênis"/"Acessórios" plain nav links inside `frontend/src/components/HeaderNav.jsx`; as of 08/08, backs all three of "Calçados"/"Roupas"/"Acessórios" as `NavDropdown` mega menus (see the `HeaderNav.jsx` entry in `docs/frontend.md` for that restructure). The endpoint itself, and its shape, are unchanged by either frontend change — only which frontend component consumes it, and how many of them are plain links vs. dropdowns, changed.

- **`produtos/views.py::CategoriaMenuView`** (`produtos/urls.py`, plain `path("menu/categorias/", ...)`, not a router registration — same "not a CRUD resource" pattern as `pedidos/views.py::FreteCalcularView`) — for every `Categoria` that has at least one `Produto`, returns the list of `Marca`s that have at least one `Produto` *in that specific `Categoria`*: `[{"id", "nome", "marcas": [{"id", "nome"}, ...]}, ...]`. A `Categoria` with zero `Produto`s doesn't appear in the response at all, and a `Marca` never appears under a `Categoria` it has no stock in — both by construction, not by a separate empty-check: the whole structure is built from one `Produto.objects.filter(categoria__isnull=False, marca__isnull=False).values(...).distinct()` query, grouped in Python, so an empty combination simply never produces a row to begin with.
- **Dedicated endpoint, not assembled client-side from the existing `GET /categorias/` + `GET /marcas/`** — considered and rejected: those two list *every* `Categoria`/`Marca` that exists, with no way to tell which combinations actually have products behind them short of also walking every `Produto`, and both endpoints (`categorias`, `marcas`, `produtos`) are paginated at 10/page — building the menu client-side would mean paging through the *entire* product catalog on every page load just to know which columns/links to show. One indexed query here does the same job in a single round trip regardless of how large the catalog grows, and keeps "don't show an empty combination" a backend guarantee instead of a frontend filtering step that every future consumer of this data would have to remember to redo.
- **`AllowAny`**, not the project's default `IsAuthenticated` — same reasoning as `ProdutoViewSet`'s read access via `IsAdminOrReadOnly`: this is catalog navigation, has to work for an anonymous visitor, and the view only ever handles `GET` (no write path to gate behind staff the way `IsAdminOrReadOnly` would). Exposes nothing that isn't already public via `GET /produtos/`. Not throttled either, for the same reason `GET /produtos/`/`GET /categorias/` aren't — it's a read against our own DB, no external/paid dependency and no abuse-worthy cost the way `/api/frete/calcular/`'s SuperFrete calls are.
- Verified via curl: response correctly omits any `Categoria`/`Marca` combination with zero matching `Produto`s; following a returned `{categoria.id, marca.id}` pair through `GET /produtos/?categoria={id}&marca={id}` (the same query the frontend's mega menu links use) returns exactly the matching product(s) — confirms the ids round-trip correctly into the existing `ProdutoViewSet.filterset_fields` filter, not just that the menu endpoint itself returns a well-shaped response.
