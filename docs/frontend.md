# docs/frontend.md

> Consulte primeiro `CLAUDE.md` na raiz do repositório — ele explica o índice de documentação e o padrão a seguir ao registrar mudanças futuras neste arquivo.

Documentação de domínio: toda a arquitetura React/Vite do frontend — componentes, páginas, contexts, padrão de formulários, tema visual. Este arquivo não é dividido por domínio de backend (produtos/pedidos/usuários) porque a maioria das páginas cruza mais de um domínio (ex.: `Checkout.jsx` mexe com pedidos, frete e pagamento ao mesmo tempo) — ficaria fragmentado sem ganho real de clareza.

React 19 + Vite + Tailwind + shadcn/ui, using `react-router-dom` for routing.

- **Brand theme (`src/index.css`, `index.html`) — added 07/08, first step of the Visual Polish phase (see "Development Status" in the root `CLAUDE.md`).** Replaces the neutral shadcn placeholder palette used since the project's initial scaffold with Royal Conceito's actual identity: predominantly black storefront, gold/amber neon signage, a crown symbol — premium/streetwear positioning, not the generic gray-on-white shadcn default.
  - **Dark mode is now the site's default**, not a toggle — `index.html`'s `<html>` tag carries `class="dark"` unconditionally, activating the `.dark` CSS block that already existed in `index.css` since the initial shadcn setup but had never actually been applied anywhere (confirmed by grepping the codebase for any `next-themes`/`useTheme`/manual `classList` toggle before this change — none existed). No light/dark switcher yet — deliberately out of scope for this pass, same "not now" reasoning as everything else marked for a later polish pass; the `:root` (light) block is untouched and still there if a toggle is added later.
  - **Gold accent, not a full recolor:** only `--primary`/`--primary-foreground`/`--ring` changed in the `.dark` block — every other neutral (background, card, border, muted, secondary, foreground) is untouched, so the gold reads as a deliberate accent (primary buttons, active/selected states, links, focus rings) against black/gray, not a wash of yellow over the whole UI. `--accent` was deliberately left neutral too, not gold — it backs hover/expanded states on `outline`/`ghost` buttons and dropdowns (`button.jsx`), which are secondary UI, not calls to action; making every hover state gold would have diluted the accent's meaning as "this is the important action" rather than reinforced it.
  - **Palette choice:** `--primary: oklch(0.72 0.13 85)` — computed (not eyeballed) from sRGB `#CA9D33`, inside the requested `#C9A227`–`#B8860B` range, expressed in OKLCH to match every other variable already in this file rather than mixing color spaces. `--primary-foreground` stays near-black (`oklch(0.145 0 0)`, matching `--background`) rather than white: computed contrast ratios (relative-luminance formula, not guessed) are ~7.9:1 for black text on this gold vs. ~1.9:1 for white — black clears WCAG AA's 4.5:1 for normal text with real margin, white would fail outright. The same gold used directly as text/link color on the near-black `--background` also measures ~7.9:1 (same two colors, contrast is symmetric). `--ring` reuses the same gold at 50% alpha (`oklch(0.72 0.13 85 / 50%)`) rather than full opacity — a subtle branded focus glow, not a solid gold outline, consistent with how `--border`/`--input` already use alpha-based whites in the pre-existing `.dark` block.
  - **No component files touched** — `button.jsx`, `card.jsx`, `input.jsx`, `label.jsx`, `select.jsx` are all unchanged; every one of them already consumes `--primary`/`--ring`/etc. via Tailwind's `bg-primary`/`text-primary`/`ring-ring` utility classes (confirmed by reading each), so the new palette propagates automatically everywhere those tokens are used (buttons, links, selected/focused states, the cart-count badge in `Header.jsx`) with zero component-level edits, per the "CSS variables only" constraint for this pass.
  - **Verified, not just assumed, that the change wouldn't break contrast:** grepped every page/component for hardcoded Tailwind colors (`bg-white`, `bg-black`, `bg-gray-*`, `text-gray-*`, literal `text-black`/`text-white`) that could clash with a suddenly-dark background — none exist in `Catalogo.jsx`, `Login.jsx`, `Checkout.jsx`, or the shared components they render (`ProdutoCard.jsx`, `Header.jsx`, `ProdutoImagemPlaceholder.jsx`); everything already routes through the same semantic tokens this fix updates. `npm run build` and `npm run lint` both re-run clean after the change (the 4 lint errors present are pre-existing, in files this change never touched — `button.jsx`'s fast-refresh export warning, same in `AuthContext.jsx`/`CartContext.jsx`, and an unrelated `ProdutoDetalhe.jsx` effect warning). Not manually verified in-browser — browser automation is off-limits on this project (see below); the user checks visual changes manually.
  - **One pre-existing component was left visibly out of step with the new theme at the time — since fixed, 11/08.** `PedidoStatusBadge.jsx` originally hardcoded light-mode Tailwind pill colors (`bg-blue-100 text-blue-700`, etc. — a light, near-white background with dark text) that were fine against the old light default but rendered as a bright pastel box against the new near-black background on `MeusPedidos.jsx`/`PedidoDetalhe.jsx`; deliberately left alone at the time, per the "don't touch individual components" scope of the brand-theme pass itself. **`TrocaDevolucaoStatusBadge.jsx` (added 10/08, see "Trocas e Devoluções" below) was modeled directly on `PedidoStatusBadge.jsx` and copied the same light-mode pattern** (`bg-green-100 text-green-700`, etc.) — so the same fix had two call sites to update, not one, by the time it landed. **Fix (11/08):** both components' `STATUS_CLASSES` lookup tables were recolored for the dark theme — a semi-transparent `bg-{cor}-500/15` fill with `text-{cor}-300` for every status whose hue has no equivalent theme token (blue/amber/purple/green — the theme only defines neutral + gold `--primary`), and `bg-destructive/15 text-destructive` (reusing the theme's own `--destructive` token, already dark-mode-tuned, the same convention `Login.jsx`/`EnderecoForm.jsx`'s error banners already use) for the one status in each set that's semantically negative (`cancelado` on `Pedido`, `rejeitada` on `SolicitacaoTrocaDevolucao`) — same per-status color assignment as before, just recolored. Confirmed via `grep` afterward that no other component in `src/` still has the old `bg-*-100 text-*-700`-style light pill pattern. `npm run lint`/`npm run build` both re-run clean (same 4 pre-existing, unrelated errors as noted above — none in either badge file).
- **`src/lib/axios.js`** — shared Axios instance (`api`), `baseURL` from `VITE_API_URL` (defaults to `http://localhost:8000/api`), `withCredentials: true` so the httpOnly JWT/CSRF cookies flow cross-origin
  - Request interceptor attaches `X-CSRFToken` (read from the `csrftoken` cookie) on state-changing methods (`post`, `put`, `patch`, `delete`), matching the backend's CSRF enforcement
  - Response interceptor catches a `401`, calls `POST /token/refresh/` once (deduped via a module-level `isRefreshing`/`refreshPromise` pair so concurrent 401s share a single refresh call), then retries the original request; requests already flagged `_retry`, or the refresh call itself, are not retried again to avoid loops
- **`src/contexts/AuthContext.jsx`** — `AuthProvider` + `useAuth()` hook; on mount calls `GET /me/` to hydrate `user` (`isLoading` covers this initial check); exposes `login(username, password)` (`POST /token/`, then `GET /me/`), `register(dados)` (`POST /registro/`), `logout()` (`POST /logout/`, always clears local `user`), and — **added 08/08** — `atualizarPerfil(dados)` (`PATCH /me/`); `isAuthenticated` is derived as `!!user`; on failure, `login`/`register`/`atualizarPerfil` all resolve `{ success: false, error }` where `error` is the raw DRF error payload (`{ detail }` or `{ campo: [...] }`), not a pre-extracted string — kept raw so callers can map it onto a form (see `src/lib/apiErrors.js`). `atualizarPerfil()` calls `api.patch("/me/", ...)` directly inside this context, same as `login`/`register`/`logout` already do — every account-identity endpoint is called straight from `AuthContext`, not through a separate `src/api/` module, since `user` state only lives here; on success it sets `user` directly from the response body (the updated `MeSerializer` payload) instead of a separate follow-up `GET /me/` — unlike `login()`, which has no choice but to call `GET /me/` separately (`POST /token/` returns no user data, only sets cookies), `PATCH /me/`'s own response already *is* the full, current `MeSerializer` shape, so a second round trip would just re-fetch the exact same thing.
- **`src/contexts/CartContext.jsx`** — `CartProvider` + `useCart()` hook; cart state (`itens`) is frontend-only — loaded from and persisted to `localStorage` (key `"carrinho"`, via a `useEffect` on every change) — with no backend persistence until a `Pedido` is created at checkout; each item is keyed by `variacaoId` (a `Variacao` already belongs to exactly one `Produto`, so it's a sufficient unique key) and carries a snapshot of `estoque` taken when added; exposes `adicionarItem(produto, variacao, quantidade)` (merges into an existing line for the same `variacaoId` instead of duplicating), `removerItem(itemId)`, `atualizarQuantidade(itemId, novaQuantidade)` (clamped to `[1, estoque]` — dropping to 0 removes the line rather than leaving a zero-quantity row), `limparCarrinho()`, and derived `totalItens`/`totalValor`
- **`src/components/PrivateRoute.jsx`** — route guard using `useAuth()`; renders a loading state while `isLoading`, redirects to `/login` (via `Navigate replace`, passing `state={{ from: location }}`) when not authenticated, otherwise renders the nested route (`Outlet`)
- **`src/App.jsx`** — wraps the app in `AuthProvider` + `CartProvider` (independent of each other, order doesn't matter) + `BrowserRouter`, renders `Header` above `Routes` and `Footer` below `Routes` (added 10/08, see `Footer.jsx` entry below). Routes: `/` (`Catalogo`, product grid), `/produtos/:id` (`ProdutoDetalhe`), `/carrinho` (`Carrinho`, public — no `PrivateRoute`), `/login` and `/registro` (real forms, see below), `/sobre`, `/privacidade`, `/contato`, `/termos-de-uso`, `/politica-de-trocas` (public institutional pages — `/sobre`/`/privacidade` added 10/08, `/contato`/`/termos-de-uso`/`/politica-de-trocas` added 13/08 — see `Sobre.jsx`/`Privacidade.jsx`/`Contato.jsx`/`TermosDeUso.jsx`/`PoliticaTrocas.jsx` below), and behind `PrivateRoute`: `/checkout` (`Checkout`), `/pedido-confirmado` (`PedidoConfirmado`, inline placeholder — shows `location.state.pedidoId` when present), `/meus-pedidos` (`MeusPedidos`, order history), `/meus-pedidos/:id` (`PedidoDetalhe`, single order view), `/meus-enderecos` (`MeusEnderecos`, saved-address management), `/meus-favoritos` (`MeusFavoritos`, added 18/08, favorited products), and — restructured 10/08, see `MinhaConta.jsx` below for the full "Perfil.jsx → hub" story — `/minha-conta` (`MinhaConta`, account hub), `/minha-conta/dados` (`MinhaContaDados`, email/telefone + password), `/trocas-e-devolucoes` (`TrocasDevolucoes`, troca/devolução requests). **`path="*"` (added 13/08), last entry in `<Routes>`, renders `NotFound`** — a catch-all outside every other group (including `PrivateRoute`'s), so it matches any URL none of the routes above recognized, regardless of auth state.
- **`src/components/Header.jsx`** — redesigned 07/08 (third step of the Visual Polish phase, see "Development Status" in the root `CLAUDE.md`), replacing the earlier single-`MegaMenu` version (added earlier the same day — see the `NavDropdown.jsx`/`HeaderNav.jsx` entries below for what replaced it) with a classic 3-column e-commerce layout: `grid grid-cols-[auto_1fr_auto]` — logo (auto-width, left), central nav (`1fr`, truly centered), actions (auto-width, right). A plain flex `justify-between` was deliberately not kept for this: it only visually centers a middle item when the left/right sections happen to be equal width, which isn't guaranteed here (the new central nav's width varies with viewport/wrapping) — the grid's `1fr` column centers correctly regardless. **The right-hand actions column is unchanged from before this redesign, just relocated into its own grid column**: username + "Sair" (authenticated) or a "Login" button, cart icon + badge, "Meus Pedidos"/"Meus Endereços" links — still minimal/unstyled (full visual polish of these specific elements still tracked under "Not yet done" in the root `CLAUDE.md`), still with no responsive collapsing of their own. Only the old catch-all "Categorias" trigger was actually replaced by this pass, not this right-hand cluster. **"Meus Pedidos"/"Meus Endereços" removed from this cluster 14/08** — once `MinhaConta.jsx` existed as a hub already listing both as navigation rows, the two links here were pure duplication; the cluster is now just the cart icon and the account-icon-or-login `Link`. **Updated 2026-08-07 — the "Royal Conceito" text in the logo `Link` was replaced with the real brand logo image** (`src/assets/logoroyalconceito.png`, imported via the `@` Vite alias), the link's `to="/"` behavior unchanged. Once "Minha Conta" became its own hub page with real, clickable rows for everything the dropdown used to reveal (username display, "Perfil"/now "Informações da Conta", and "Sair" — see `MinhaConta.jsx` below), the icon here had nothing left to reveal on hover/tap — it's just a destination now, same idiom as the cart icon `Link` right above it. This also removed the desktop/mobile split (the two separate blocks with different interaction mechanisms, `group-hover` vs. `<details>`/`<summary>`) entirely — a plain `Link` needs no device-specific reveal mechanism, so `Header.jsx` is measurably simpler after this change, not just relocated. `user`/`logout`/`useNavigate` are no longer used in this component at all (logout moved into `MinhaConta.jsx` itself) — removed from the `useAuth()` destructure and the import list rather than left unused.

Purely presentational: takes a `label` and `children` (the panel's own content/layout, fully owned by the caller — a grid of columns, a flat list, whatever fits), and only handles the open/close mechanics, reused unchanged for both "Roupas" and "Marcas" below despite their panels looking structurally different (multi-column grid vs. flat list) — see "Desktop"/"Mobile" bullets under `HeaderNav.jsx` for those mechanics (hover/focus-within reveal + `hidden` for tab-order on desktop, native `<details>`/`<summary>` accordion on mobile) — unchanged from the original `MegaMenu.jsx` implementation, just no longer coupled to one specific "Categorias" dataset.
