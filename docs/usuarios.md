# docs/usuarios.md

> Consulte primeiro `CLAUDE.md` na raiz do repositório — ele explica o índice de documentação, o mecanismo de autenticação (transversal), e o padrão a seguir ao registrar mudanças futuras neste arquivo.

Documentação de domínio: **autenticação de usuário, PerfilUsuario, endpoints de conta** (registro, dados da conta, senha). O mecanismo de JWT/cookies em si (compartilhado por toda a API) está documentado no `CLAUDE.md` raiz, em "Authentication mechanism" — este arquivo cobre só o que é específico do domínio de usuários.

## Key Model Relationships

- **PerfilUsuario** (`usuarios/models.py`, added 10/08 — `usuarios` app's first real model; before this the app only had `RegisterSerializer`/`MeSerializer`/`MeView` around the built-in `User`) → `OneToOneField` to `User` (`related_name="perfil"`, **CASCADE**, not `PROTECT` — same reasoning as `Endereco.usuario`: this is profile data, not sale/order history, so there's no reason for it to survive the account itself being deleted). Holds `telefone` (`CharField(max_length=20, null=True, blank=True)`, no format/mask enforced — same "don't invent a validation rule the frontend doesn't also enforce" reasoning as `Endereco.cep`'s regex being the one exception, not the norm). **Deliberately a separate model, not a new field on `User` directly** — Django's own docs recommend this exact pattern (a profile model with a `OneToOneField` back to `User`) precisely because modifying `django.contrib.auth.models.User` itself would mean swapping `AUTH_USER_MODEL` for a custom user model *before* the first migration ever ran, which didn't happen when this project started; retrofitting that now, this deep into the project, would be a far bigger migration than adding one small related table. **No `PerfilUsuario` row exists for any account created before 10/08** (no backfill, no migration `RunPython` — same "don't guess/backfill a value nobody actually knows" principle already used for `Variacao.peso`'s placeholder default, `Produto.imagem_url`, etc.) — `get_or_create` is what actually creates the row, the first time anyone sets a phone number (see `AtualizarPerfilSerializer.update()`, "Authentication & Authorization" below), not a one-time data migration. Exposed on `MeSerializer` via a `SerializerMethodField`, not `CharField(source="perfil.telefone")` — confirmed via shell (not assumed) that accessing `user.perfil` when no row exists raises `RelatedObjectDoesNotExist`, and separately confirmed that `getattr(user, "perfil", None)` safely returns `None` in that case (Django's `RelatedObjectDoesNotExist` genuinely is an `AttributeError` subclass, which is what makes `getattr`'s default kick in) — `get_telefone()` uses that `getattr` explicitly rather than leaning on however DRF's own field-resolution machinery happens to handle the same exception today.

### Authentication & Authorization

- `/api/registro/` uses `AllowAny`
- `usuarios/views.py::MeView` (`GET /api/me/`, `IsAuthenticated`) returns the current user via `MeSerializer` (id, username, email, is_staff, **telefone — added 10/08, see `PerfilUsuario` under "Key Model Relationships" above**) — used by the frontend to hydrate/validate the session on load and after login. **`PATCH /api/me/`, added 08/08** (same view, same URL — a partial update of the same "current user" resource, not a separate endpoint): validates via `AtualizarPerfilSerializer` (`email`, and — added 10/08 — `telefone`) and returns the updated user via the same `MeSerializer`, so a successful save gives the frontend the exact same shape `GET`/login already produce. **`username` is deliberately not editable through this endpoint at all** — not `read_only`, simply absent from `AtualizarPerfilSerializer.Meta.fields`, so a client sending it is silently ignored (same "protect by omission" pattern used elsewhere in this file, e.g. `Pedido.usuario`): `username` is the login identifier (`POST /api/token/` takes username/password, there's no login-by-email flow in this project), so letting it change risks a user locking themselves out of saved/autofilled credentials for no real benefit — nothing in the UI treats username as an editable "profile" field beyond the Header greeting. `email` is the one field that makes sense to self-serve, since it's an ordinary contact field with no auth-identifier role. `AtualizarPerfilSerializer.validate_email()` rejects an email already used by a *different* user (`User.objects.exclude(pk=self.instance.pk).filter(email=value).exists()`) — **a real, pre-existing inconsistency this doesn't fix:** `RegisterSerializer` still has no equivalent check, so two accounts can still be *registered* with the same email even though one of them can no longer *update into* colliding with the other; flagged, not fixed, since closing the registration-side gap is a separate, unrelated task. Verified via curl: a valid new email returns `200` with the updated `MeSerializer` payload; an invalid format returns `400` with `{"email": ["Insira um endereço de email válido."]}` (Django's own `EmailField` validation, free); an email already belonging to another real account returns `400` with `{"email": ["Este e-mail já está em uso por outra conta."]}`; a payload also containing `username` still returns `200` with the username unchanged; a request missing the `X-CSRFToken` header still gets a `403` (`CookieJWTAuthentication`'s CSRF enforcement applies to `PATCH` the same as any other state-changing method, no special-casing needed). **`telefone` (10/08): `AtualizarPerfilSerializer.update()` pops it out of `validated_data` (it isn't a `User` field — `Meta.model = User` — so DRF's default `ModelSerializer.update()` would try `User(**validated_data)` and blow up on an unrecognized kwarg) and, only when the request actually included `telefone` at all (not just when it's falsy — an explicit `""` clears a saved number, while omitting the field on a partial `PATCH` must leave it untouched), writes it via `PerfilUsuario.objects.get_or_create(usuario=instance)`.** Verified via curl: `PATCH {"telefone": "(11) 91234-5678"}` persists and round-trips on the next `GET /api/me/`; a follow-up `PATCH {"email": "..."}` (telefone omitted) leaves the previously-saved telefone intact, confirming the "only touch it when present" guard actually works and doesn't implicitly null it out.
- **`POST /api/me/senha/`** (`usuarios/views.py::AlterarSenhaView`, `IsAuthenticated`, added 10/08) — a separate view/route from `MeView` above, not a third HTTP verb on it: changing a password has its own input shape (`senha_atual`/`nova_senha`, neither of which is the `password` column on `User` directly — always set via `set_password()`, never assigned raw) and its own failure mode (wrong current password) that doesn't fit `MeSerializer`'s "current user" shape at all. `usuarios/serializers.py::AlterarSenhaSerializer` (a plain `Serializer`, not a `ModelSerializer` — same reasoning) validates `senha_atual` via `user.check_password()` (400 `{"senha_atual": ["Senha atual incorreta."]}` if it doesn't match) and `nova_senha` via Django's own `validate_password()` (the same `AUTH_PASSWORD_VALIDATORS` from `core/settings.py` a Django-admin-created superuser's password already has to satisfy — minimum length, not-too-common, not-all-numeric, not-too-similar-to-the-username/email via `user=` being passed through). **A real, pre-existing inconsistency this doesn't fix, flagged the same way the duplicate-email gap on `RegisterSerializer` already is:** `RegisterSerializer` still never calls `validate_password()` at all, so a brand-new account can still be registered with a trivially weak password even though this endpoint now enforces real strength rules on every *change*. Not throttled, unlike `/api/token/`/`/api/registro/` — those are public (`AllowAny`) and brute-forceable by definition; this one is `IsAuthenticated` and already requires knowing the current password (itself already behind login rate-limiting), so the same class of risk doesn't apply the same way. **Verified via curl, the full real-world loop, not just the endpoint in isolation:** wrong `senha_atual` → `400`; correct `senha_atual` + a weak `nova_senha` (e.g. `"123"`) → `400` with all three `validate_password()` messages (too short, too common, entirely numeric); correct `senha_atual` + a valid `nova_senha` → `200`; a subsequent `POST /api/token/` with the *old* password → `401`; the same call with the *new* password → `200` — confirming the change is real, not just a 200 with no actual effect.
